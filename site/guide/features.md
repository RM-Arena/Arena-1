# 训练、对战与回放

Arena-1 的一次完整使用流程是：**选赛季 → 看懂或开发策略 → 选择阵容对战 → 看结果与回放 → 修改策略再试**。2027 与 2026 共用这些功能，阵容数量与比赛规则随赛季变化。

[![策略开发与比赛流程：创建任务、开发练习、提交入库、对战复盘、再次迭代](/media/strategy-workflow.svg)](/media/strategy-workflow.svg)

*Agent 在开发阶段写代码；进入比赛后，由提交的 Python 程序每秒决策 10 次。*

## 导出 MP4 视频

在对战页的「视频导出格式」中选择 **MP4（推荐）**，点击「录制 MP4」开始，
点击「停止并导出」结束。可录制实时比赛，也可先打开数据回放，选择镜头和播放速度后再录制。
视频记录的是录制期间播放的画面，包含比分、倒计时、结果叠层与合成音轨，分辨率为 1920 × 1080、30 FPS。

MP4 使用 H.264 视频和 AAC 音频，在本机转码，不上传到外部服务；桌面安装包自带转码组件。
停止录制后等待「正在生成 MP4」完成，再选择保存位置。也可以选择 WebM，停止后直接保存原始录像。
MP4 转码失败时会保留原始 WebM，并显示错误原因；点击「保存原始 WebM」即可下载，
或明确丢弃后重新录制。单次 MP4 导出的原始录像上限为 1 GiB，时长上限为 1 小时。

## RM 对战：先比较策略

RM 对战要求双方使用同一套硬件阵容。2027 固定五个位置，2026 固定六个位置；可为每个位置选择该赛季合规的型号，但双方构型一致。

![2027 出战机库中的机器人与合规提示](/media/rmuc2027-lineup.jpg)

*型号名称说明硬件，位置编号说明它在队内的身份。型号不合规时，界面会解释原因。*

建议第一次保留默认阵容和示例策略。之后每次实验只改一个因素，例如保持阵容、对手与种子相同，只改步兵的抢点路线。比赛中的弹丸、碰撞、血量、资源与判定均由引擎处理，策略不能直接修改规则结果。

如果阵容改变，已有全队策略可能不再适用。只有与当前阵容匹配的提交才可用于对应 RM 对战，必要时先创建新的开发任务。

## 自由对战：按型号与策略组合 {#free-battle}

自由对战允许两方使用不同的数量、重复型号与战术组合。每张可选策略卡对应一个机器人型号和一种打法；你可以为同型号搭配不同策略，也可以把常用组合保存为卡组。

![2027 自由对战的型号、战术与两方卡组](/media/rmuc2027-free-battle.jpg)

*先选当前赛季合规的型号，再选择每次部署使用的策略。2027 每方最多一套空中机器人系统。*

一个可操作的对照实验：红方使用抢点步兵，蓝方使用守点步兵，先从少量机器人开始，观察路线、视野和火力，再逐步加入其他兵种。

| 控制方式 | 怎样运行 | 适合什么实验 |
| --- | --- | --- |
| 独立控制 | 每次部署使用各自的单机策略，内部状态分开 | 研究重复型号、局部协作、同型号不同打法 |
| Team 全队控制 | 一份全队策略读取实际部署并控制本方所有机器人 | 研究集中调度与不对称阵容 |

两种方式可以分配给不同队伍。选择全队控制时，策略也应能识别实际阵容，不能假设部署编号一定等于型号编号。自由对战改变的是出战组合，不会取消赛季规则与型号合规要求。

## 训练：生成一次有期限的开发任务

训练页提供四种方式：

| 模式 | 你开发什么 | 适合谁 |
| --- | --- | --- |
| 全队统筹 | 一份控制全队的程序，2027 五台 / 2026 六台 | 想研究完整战术，或第一次开发 |
| 单机专精 | 固定位置的一份程序，之后与其他位置组队 | 只想专注一个兵种或技能 |
| 多机协同 | 每个位置一份程序，2027 五份 / 2026 六份 | 研究消息、分工与独立决策 |
| 自由适配 | 某型号可重复部署的单机程序 | 自由对战、重复型号与变化阵容 |

![训练页中的开发方式、任务名称和开发计时](/media/training.jpg)

*这张历史截图来自 2026，旧版“六机协同”在当前界面中为“多机协同”。2027 任务生成五个位置的资料；请先在当前训练页选择赛季。*

选择赛季、模式、必要的阵容和开发时间后，点击创建任务。**计时从创建时开始**，包含阅读、编码、练习和提交；截止前最后一次成功提交的版本成为参赛版本。创建后显示的 `AGENT_TASK.md` 路径就是交给 Agent 的入口。

从命令行创建工作区时，创建和启动计时是两个步骤，不能照搬训练页的自动计时假设。详细命令见[策略开发](./strategies)。

## 策略库：先看它怎么打

策略库使用 `showcase.json` 战术卡解释每份策略的打法，提供生成者、控制模式、战术与标签等筛选，以及风格雷达、比赛阶段、地图路线和关键决策。

![战术卡内容示意：身份、风格、阶段、地图与关键决策](/media/strategy-card-guide.svg)

*展示来自策略作者填写的战术卡，应结合实际回放判断；“进攻强”“善于协同”等描述不等于胜率保证。*

预置策略按型号与战术集中收纳，默认可以折叠浏览。上传自己的策略时，需要提供代码和合格的展示文件；只改说明不会改变代码版本和 Elo。

## 机器人模型与自定义外观

在策略库的“机器人模型”页查看硬件或上传 `.glb` 外观，再在开赛前“机器人外观”中选用。

**外观与性能是两回事。** 换一辆看起来更大的车，并不会增加血量、碰撞尺寸、速度或火力；比赛仍使用原型号的硬件参数与规则。真正比较硬件能力时，应切换出战型号并检查赛季合规。

## 观战：把动作与资源联系起来

比赛包括赛前自检、倒计时、实时场景、击毁播报与赛后结果。观战时可以切换镜头、跟随机器人、暂停和倍速，也可以查看金币、血量、弹药、热量与机构进度。

2027 尤其要把三件事一起看：**控制度变化、前哨控制状态、基地保护**。某台机器人暂时没有射击，也可能在维持卡片、等待冷却、装配科技或安装发射机构。

赛后面板、MVP 与伤害统计有助于复盘，但不能替代规则判胜；排行榜 Elo 按策略版本累计，手动结束和含策略错误等不满足计分条件的比赛不会更新评分。

### 赛后流程：数据面板 → 对局高光 → MVP {#highlights}

一场比赛结束后按 **胜利演出 → 数据面板 → 对局高光 → MVP 结算 → 回到战场** 走完，每一步都可以手动跳过：

- **数据面板**放在高光之前，出厂时沿用赛前过场那支主题曲（让赛前铺垫与赛后复盘听上去是同一场演出）；装了 `results-theme.m4a` / `.mp3` 就整段换成你指定的曲子。
- **对局高光**紧接着数据面板：放完（或跳过）就进入 **MVP 结算**，所以一场比赛的收尾是"先看比赛怎么赢的，再看是谁赢的"。
- **MVP 结算**沿用 `mvp.m4a`；遇到不解码 AAC 的浏览器会退到 `victory.m4a`，不会静音。卡片上「返回数据面板」回到面板（不会再自动跳转），「回到战场」结束整个赛后流程。
- **对局高光放的是这场比赛的录像本身**，不是重新摆拍的卡片：片段从裁判事件流里剪出（**最多 6 段、每段 5 秒**），排序偏向「能不能说明这局怎么赢」而不是单纯的人头数：机器人对前哨站/基地装甲打出的成段结构伤害、无人机连续撞甲 > 本局输出最高机体的峰值窗口（标题「输出王」，说明总伤害里多少打在机器人、多少打在建筑）> 多杀（8 秒内同一台机的连续击毁算一段，标题为「双杀 / 三连击 / 四连击」）> 击毁前哨站或打穿基地装甲 > 能量机关激活与 3 / 4 级装配 > 连续火力压制；**单杀只在前面的素材凑不满四段时兜底**。然后**由服务端从裁判的逐帧日志里只切出这些窗口**（整场回放有几百 MB，整份加载会把浏览器主线程卡死几秒），每段自带 **1.5 秒走弹**再播 5 秒，所以能看到弹道抵达、装甲板爆火的真实过程。切片通常 1～2 秒，期间画面显示「正在从本场回放中剪出高光片段…」。播放时镜头切到该段主角机体跟随；无人机段会直接跟随执行撞击的那一架小无人机，而不是停在机库上。跟随模式里选中空中机器人（机库）不会跟拍机库本体，而是高亮它的全部无人机并自动跟随领飞的一架，也可以在下拉框或战场上直接点选单个无人机单独跟随。画面上只叠一层广播式 HUD：左上角 `HIGHLIGHT 01/06` 与比赛时钟，左下角下三分之一（标题、说明、主角、结构/峰值/本段伤害、击毁、进度点与 5 秒进度条），右下角「跳过高光」。全部放完自动进入 MVP，随时也能跳过。所有片段共用同一条背景音乐：从第一段起一直连着放，切到下一段（或取消切片等待）都不会从头重来。
- 只有当这场比赛**的逐帧数据已经不在内存里**（例如切到回放、重启服务后）或**根本没有可剪的时刻**时才退回原来的卡片版（整机渲染图、被击毁机体卡片、进度点）；完全没素材时如实提示「本局没有留下可用的高光素材」，4 秒后自动进入 MVP 结算，绝不凭空补镜头、也不会把人卡在一张空白的战场上。

**换成自己的音乐。** 每个提示位都留了一个覆盖槽：`<cue>-theme.m4a`（其次 `.mp3`）排在出厂文件之前，所以**放文件就行，不必覆盖仓库里的素材，也不用改代码**，刷新页面生效：

| 时刻 | cue | 出厂文件 | 覆盖槽 |
| --- | --- | --- | --- |
| 倒计时「5」起播，**先完整播一遍你装的那首** | `match` | **无**（只用你装的那首） | `match-theme.m4a` / `.mp3` |
| 那首播完之后（约 4 分钟起）**循环的**是老曲 | `match_alt` | `summoning-glory.m4a`（→ `.mp3`） | — |
| 赛前过场 / 选边（RM 对战） | `pick` | 赛前过场主题 `home.mp3` | `pick-theme.m4a` / `.mp3` |
| 赛后数据面板 | `results` | 赛前过场主题 `home.mp3` | `results-theme.m4a` / `.mp3` |
| MVP 结算 | `mvp` | `mvp.m4a`（→ `victory.m4a` 兜底） | `mvp-theme.m4a` / `.mp3` |
| 对局高光 | `highlight` | 未出厂，回落到 `victory.m4a` | `highlight-theme.m4a` / `.mp3`，或沿用旧的 `highlight.m4a` / `.mp3` |

局内音乐是**一首开场 + 一首循环**：倒计时出现「5」（视为已进入局中）先用你装好的 `match-theme.*` **从头完整播一遍**（不循环），这一遍放完就自动接到仓库自带的 `summoning-glory.m4a|mp3`（`match_alt`）并**一直循环到本局结束**——也就是开场是"纯享版"，之后的循环是老版 Summoning Glory。每开一局都按这个顺序重来（回放不占这次开场，直接整局用老曲）。**同一局里怎么改倍率都不会换曲、也不会从头重放**；第一首还没放完就暂停 / 切倍率，回来接着放，放完才交接。仓库自带的旧比赛主题仍然不在 `match` 这条链里：**没装文件时这一局不静音，直接从老曲开始循环**（反正循环段本来就是它）。`pick` 接管**整个赛前过场**：过场动画一出现就换成准备阶段的曲子，选边 / 选机体就叠在它上面，一直到倒计时才交给局内曲（自由对战仍用自己的过场曲，只有人在选边时才切到这首）。赛后关掉结算、回到「准备下一场」的布置界面时**不放背景音乐**（数据面板那首只属于结算），要等再开一场、进入过场 / 选边时才重新起乐。同一首曲子会同时写出 `.m4a`（AAC）和 `.mp3`：前者体积更小，后者保证在不带 AAC 解码的浏览器（Chromium 定制版、VS Code 预览、桌面壳）里也能出声，播放器会按 m4a → mp3 的顺序挑第一个能解码的。

一条命令就够（文件放哪都行，有 ffmpeg 会自动抽掉视频轨、转成 m4a + mp3；没有 ffmpeg 就把现成的 mp3 / m4a 复制过去）：

```bash
python scripts/install_music.py "D:/music/我的曲子.mp3" --slot match
python scripts/install_music.py "D:/music/highlights.mp3" --slot highlight
python scripts/install_music.py "D:/music/interlude.mp3" --slot results
python scripts/install_music.py "D:/music/mvp.mp3" --slot mvp
```

槽位文件不存在时，浏览器会先请求一次并拿到 404，再退到出厂文件——**控制台里这几条 404 是正常的**，代表提示位在探测覆盖文件。播放列表里的 MP3 兜底是为了照顾不解码 AAC 的浏览器（Chromium 定制版、VS Code 内置预览）。仓库不附带任何来自视频网站的音频：想听哪首，请自己提供你有权使用的文件（自己的录音或已授权的音源），项目只负责把它接到对应时刻。


## 第一视角驾驶：比赛中手动接管一台机器人 {#pilot}

**赛前自检与倒计时。** 自检（阵容过场）阶段可以点「跳过」直接进入倒计时，但**5-4-3-2-1 一旦开始就不能跳过**：比赛时钟与局内主题曲都以它为准，服务端收到倒计时期间的跳过请求会直接拒绝（`400 倒计时不可跳过`），页面也不会显示跳过按钮，只留一行「比赛即将开始 · 倒计时不可跳过」。**过场每一段至少显示 2 秒**（开场 → 红方队卡 → 红方各机体 → 蓝方队卡 → 蓝方各机体 → 面交锋，共 `机体数 + 4` 段），所以自检时长是**自适应**的：选边 / 选机体花掉的时间会把自检时钟撑长（`POST /api/control {"command":"extend_prematch","seconds":n}`，时钟与对外公布的时长同时增加，已播的进度不受影响），倒计时相应顺延，而不是把某段卡片压缩成零点几秒；延长总量有上限（客户端累计 90 s、单次 30 s），不会因为有人离开而永远卡在赛前。局内主题曲从 **「5」出现的那一刻**就起播，而不是等比赛开始。

实时比赛进行时，画面右上角、全屏按钮左侧有一枚「驾驶菜单 P」小按钮，也可以直接按 **P** 打开面板。面板里只有一颗 **LINK START**：点下去以后面板**滑到画面右侧变成一条机库栏**（宽度自适应：`clamp(184px, min(22vw, 30vh), 300px)`，小窗 / 矮窗自动收窄并压紧行距，不会吃掉半个战场；栏体配色跟着当前浏览的阵营走——看红方是红色强调，看蓝方是蓝色强调）、镜头同时切到**俯视全场**，整块场地铺满画面（相机距离由场地尺寸与画布宽高比算出，取能完整框住 28 × 15 m 的距离再拉远 25 %，即场地只占画面的 **80 %**，屏幕上方那片广播记分牌就不会压住场地远端；屏幕上方就是场地远端、与小地图同向），鼠标靠近哪台机体，指针旁就浮出它的详细卡片（型号、血量、底盘功率、热量上限、单发伤害、机动速度、整机质量与底盘特性）——**镜头还会沿视线俯冲到这台机体上**，把它放到画面正中并放大到约占画面高度 30 %，指针移开就平滑拉回全场俯视；卡片固定贴在场地左下角，不会挡住正在被放大的机体。点一下那台机体——或直接点右侧机库栏里的条目——会弹出「建立神经连接？」确认页，确认后镜头**一路动态推进到第一人称**，键盘和鼠标接管这一台；点「返回」则原路收回原来的镜头模式：

**座舱配色随阵营。** 一旦接管某台机体，整块驾驶 UI 的强调色就跟着这台机体所属阵营走：接管红方时准星、弹药读数、HP / EXP / 缓冲 / 超电 条、小陀螺与超电提示、P 面板、购买与装配面板、机体卡上的 **P1** 徽标全部转为红色系（并加一圈极淡的红色边缘辉光），接管蓝方则整体转为蓝色系。这样一眼就能确认"我现在在替谁打"，也能避免在混乱的交火里误判阵营。**只影响驾驶时的座舱**：赛前选边简报、机体选择卡片、广播 HUD 仍然使用中性的仪表青，因为那时还没有"我的阵营"。

**开局选人与鼠标时机。** 点「开始对战」**直接进入战场选人**（不再弹询问窗），赛前自检阶段由镜头接管——先以**斜 45° 俯瞰全场**（距离按画布宽高比自动拉远，窄屏也能看到整块场地），场地的左右两半就是红/蓝半区：鼠标移到哪边，那半边地面就亮起队伍色、一条扫描光带沿半场推进、四个角的光柱升起、外沿竖起一道能量墙，指针处还有一枚贴地光环；**每半区上方浮着该方简报**（策略名、历史胜率、Elo、胜/负/平、上场机体数、比赛模式），悬停的那一侧才会亮起，平时压暗。**看台高亮只在选边阶段生效**：选定阵营后观众席熄灭、镜头也不再为看台拉远，焦点回到己方启动区。**场地外一律算观众席**：看台、走道和场地四周的空地都点亮一道冷青色的发光框，指针停在那里时镜头会**向后拉远约 28 %**，让整排看台进入画面，同时**建模出来的阶梯看台与观众席本身也会亮起冷青色**（离开就淡回暗色），**两个半区中间还常驻一张「观众席 · 看台」简报**（标注视角自由、随时可接管、整局交给策略），悬停时与看台一起点亮；底部提示「观众席已高亮 · 单击进入观众席」，点一下就是观众（也可以点底部中间的「观众席」按钮）。点一侧半区即选该方。镜头随即**缓动滑降**到该方**启动区的低角度三分之四视角**（约 1.2 s 的位置 / 视线双缓动，不是硬切；点「重新选边」也沿同一条曲线滑回 45° 全景）（整簇机体都在画面里），鼠标靠近哪台机体，镜头就像过场动画里的单机镜头一样**贴近那台机体**（同一套取景公式：按机体尺寸算距离、略高于机体、从车头斜前方看向车体中段），车体微微抬起并亮起队伍色光环，同时**直接复用赛前过场动画那套机器人镜头 UI 与特效**（闪光、扫光、瞄准框、逐条递增的数值条、底盘特性标签、策略 Agent 卡片、阵容进度点），点一下选定（选好还可以「重新选边」）。指针停住时目标被**锁定**，镜头推近不会因为屏幕投影变化而反复改判；只有指针明显移向另一台或离开该机体时才改判。整个选人**没有弹窗和列表**，场地和机体模型就是界面。**准备阶段不捕获鼠标**，指针留在浏览器里，可以继续点面板或跳过；倒计时结束、比赛真正开始后才自动把指针锁进画面（若浏览器因为没有用户手势而拒绝，会保留「鼠标未锁定 · 点击画面锁定」的提示）。被击毁时同样**立即释放鼠标**，方便点「立即复活」或等免费读条；只有复活后才会再次尝试捕获。场地内右键是自动瞄准，所以浏览器右键菜单、中键自动滚动、文字选择与原生拖拽都被拦截，按住右键只会锁定装甲板。你在驾驶哪台机器人，画面顶部那张机体卡上方的圆形徽标就不再是策略所属的 Agent，而是一个金色的 **P1**，标出这是人在开。

第一视角镜头就是云台本身：眼睛装在枪口高度的 1.27 倍处（`FPV_EYE_LIFT`，比之前的 1.495 低 15%，更贴近枪线又仍然越过炮管），`yaw` 与 `pitch` 都直接取引擎帧里云台的角度（20 Hz 采样之间做插值，机器人模型的炮塔/枪管用同一个插值系数摆姿态），因此**视线俯仰 = 枪管俯仰**，准星和炮口不会再各指一边；旁观别人的第一视角时才改用缓动跟随。鼠标推动云台的**目标角**并受引擎云台转速限制，是否转动由引擎决定，不会出现「镜头飞了、炮口没跟上」。低头可以看到自己的车体：驾驶时只隐藏炮塔与炮管（眼睛就在它们里面），车体、轮腿与装甲照常绘制。

**重装机器人：取矿与装配（第一人称）。** 2027 的重装机器人前期不再只能交给策略：驾驶时靠近己方矿区（`red_resource` / `blue_resource`）**按住 I**，机械臂会走「对准能量单元 → 夹取 → 收入弹仓」的完整流程，最多携带 **3 个**能量单元——两个弹仓装满后，第三个直接**夹在夹爪上**（`unit_pickup.stage = carrying`，松手、开走、离开矿区都不会丢，模型中能看到它夹在爪上，机械臂把它举在立柱前方），到核心前插入时**先消耗夹爪里那个**，再去取弹仓；到场心的**兑矿台**（`assembly` 区）**按 I** 打开装配面板，面板按规则逐条列出四级状态——一级开局可做，此后每分钟解锁一级；每级必须先完成上一级；四级一场只能完成一次；一级需要 1 个能量单元、四级需要 2 个。面板同时给出每一级的**首次 / 非首次收益**（等级、每 10 秒金币、25% / 50% 防御增益、等级上限、42 mm 解锁）。下达后由**机械臂自动完成**插入 / 抬升 / 翻转 / 旋转到目标角 / 确认这几个动作（驾驶端按引擎帧里的 `cores[].target_rotation` 与 `blocked_reason` 逐 tick 下发，人工不必同时操控五个轴），第一人称镜头会**跟着机械臂看核心**。**只要重装机器人站在己方兑矿台（`assembly` 区）的场交互模块卡上，它就处于无敌状态**：不必正在装配，也不消耗时间额度，被击毁前的保护时间用完也照样生效——打开装配面板时会显示「己方装配区内重装机器人处于无敌状态」。离开卡片（含 2 秒释放延迟）才恢复可被击穿；敌方装配区不提供保护。把机器人开到己方工位按住 **J** 就能装 42 mm——**安装本身整局任何时候都能做**；但**解锁是硬条件**：只有完成三级装配、或比赛进行到 300 − M/50 − 2N/3 秒之后，这台重装才打得出去（解锁前弹匣里有弹也扣不动扳机，首发射击才把机构从 `fitted` 定装成 `installed`）。**装好（以及开火后的 `installed` 状态）之后镜头立刻切到发射机构云台**，跟随炮管的 yaw / pitch，不再回到机械臂。尚未安装发射机构时，重装的第一人称视角就是**机械臂工位视角**：眼睛落在车体中线上、机械臂立柱前方一点，高度按重装自带的机械臂相机取（约 0.5 m，比发射机构云台的炮线低一半多），所以既能看清脚下与兑矿台，又不会把立柱顶在画面正中央。**留在第一人称的那些步骤里，视线沿大臂（升降臂 → 伸缩臂）的轴向走**，而不是跟着夹爪的姿态：夹爪自己的俯仰、滚转不会甩动画面，只有大臂抬起、伸出或收回时镜头才跟着转，所以整段取矿 / 装芯都能看到机械臂末端的动作。取矿或装配进行时，镜头会切成**和「跟随」模式一样的第三人称追车机位**（沿车头方向后退 4 m、抬高 4.4 m 俯视车体），能同时看清机械臂与大臂末端的动作；夹爪夹住第三个能量单元（`unit_pickup.stage = carrying`）或机器人离开取矿台之后，镜头**立刻回到第一人称**。进出这个机位、以及第一视角 ↔ 跟随 ↔ 广播之间的切换都是 0.5 秒缓动，不会硬切。平时（不在工作）看车头方向；视角取自与车体同一套插值姿态，不会在 20 Hz 采样之间抖动，也不会在机械臂视角与云台视角之间来回跳。装配各步的判定只要求**工具末端仍在核心上（位置 + 单元滚转）**，不再要求机械臂把工具轴线摆到某个绝对角度——倾斜核心抬升单元时腕部会顶到行程极限，过去正是这条判定把 3 / 4 级装配卡在「flipping」上。

**第一人称只显示自己和赛场态势。** 进入驾驶后保留对局正常的**顶部记分栏**（双方名称、基地/前哨血量、剩余时间、控制度与伤害、金币），唯一区别是对方机器人一侧的卡片保留正常版式，但**血量条只显示灰色占位**，弹药 / 机构读数、等级箭头与复活百分比都不公开（外观、名字与编号照常，便于认车）；窗口较窄时顶部记分栏会切到紧凑布局（只收起前哨站数字），但**机器人卡片与血条行始终保留**，不会因为窗口宽度而消失。小地图、右侧数据面板与机体详情仍然关闭，避免直接看到对手的状态与位置。视野中只保留左下角血量 / 等级经验 / 电容、画面中央的热量环与弹量，以及锁定目标提示。视角为 **64°**（比原先的 80° 收窄 20%，边缘不再把视线从准星上拉走）；广播镜头仍是 42°。

手感上：中心圆环保持 40% 透明度，但半径是原来的 4 倍（384 px 直径，短窗口自动缩到 300 / 220 px），弹量与热量挪到**圆环右侧**单独显示，不再压在准星上；鼠标灵敏度按 64° 视场等比缩放（同样手部位移转过的角度一致）；按住方向键 0.7 秒后转速线性提升到 2 倍，轻点微调、长按快转都跟手；每次输入（移动鼠标、按下**和松开**开火/移动键、按键）在无请求在途时会**立刻**下发一次，最坏输入延迟从 50 ms 降到一次往返，松键即刹；镜头读的是「已经下发的云台角」，所以准星始终骑在炮口上，不会出现镜头先到、炮口后到。复活时准星直接对齐新出生姿态的云台角，不会从阵亡位置扫回来。

驾驶时画面里只保留必要信息：**画面中央**是三条弧——血量、实时功率（对功率上限）、枪管热量——加一个固定尺寸的准星，环右侧是剩余弹量与热量读数，整组中心 HUD 统一 **40% 透明度**（原先的超电弧与缓冲内弧已去掉，它们在第一人称里没有可操作的意义）；**左下角**是编号/等级、血量、经验、缓冲能量（含功率上限）与超电两张进度条，超电与缓冲只在需要时低头确认；锁定目标时中央下方显示目标与距离。购买结果的弹量与金币来自引擎的 `ammo_purchase` 事件；买不到时引擎会回一条 `ammo_refused`，驾驶端直接显示具体原因（金币不足、本队购买批次已满、需回到补给区或需脱离交战 6 秒）。中弹时画面边缘闪一次红色暗角，和参考客户端的受击反馈一致。

**枪管热量控制按参考模拟器的做法**：每发子弹都要吃热量，热量超过上限引擎会锁枪直到冷却到 0，超过上限 +100（英雄 +200）还会触发永久热锁。驾驶面板会从「弹量与热量的变化」实测出单发热量，按下开火时只要「当前热量 + 一发余量」会越线就不发弹；这个提示**只在按住扳机时**出现（「热量封锁 · 枪口冷却中」），真正过热时才常驻显示「枪管过热 · 冷却中」，所以不会整局挂在屏幕上。余量只留一发，是因为留两发会把可开火区间压到热量条的一半以上，反而不像真车的手感。

**阵亡后镜头锁定。** 被击毁时画面立刻转为灰度，镜头保持在被击毁时的姿态不再跟随鼠标与方向键，屏幕中央叠出「已阵亡」与复活读条（进度与倒计时取自引擎的 `respawn_progress / respawn_required`），以及一个「立即复活」按钮：读条走完会**免费**复活，也可以花 `ROUNDUP(已进行分钟数)×80 + 等级×20` 金币立刻复活——保留阵亡前的等级与经验，血量回满，并获得 3 秒的「虚弱 + 无敌」；复活瞬间镜头直接接到新的出生姿态，不会从旧位置旋转过去，3 秒结束后操作照常。金币不足时按钮下方直接说明还差多少。完全控制的前哨站增益点会解除「虚弱」及其对应的无敌状态，与补给区增益点一致。

弹药价格与批次完全按规则执行：17mm 补给区 10 发 / 10 金币、远程 100 发 / 150 金币；42mm 补给区 1 发 / 10 金币、远程 10 发 / 150 金币，并有团队购买上限。补给区/完全控制前哨站的本地购买可以按任意发数下单、金币按比例扣（例如 17mm 买 7 发扣 7 金币），远程订单仍然必须按批次整数倍。引擎的规则结算每两个比赛节拍跑一次，所以驾驶端把一次下单**排队到下一个结算节拍**再下发，只买一次、不会再出现「按了没反应」。远程订单只有在脱离战斗后才会被引擎接受，送达前弹量不会增加。金币是**本局累计**（击杀、控制区等），开局为 0，所以开局那一波必须回到基地/补给区才能补弹——左下角状态栏会显示当前金币，按下 O / H 时也会先按服务端公布的**批次、价格与团队购买上限**计算能否下单，再判断交战计时；任何一项不满足都会直接说明原因（金币不足、批次上限、补给区/脱离交战条件），不会再出现「条件看起来满足却买不到」。

**弹丸散布。** 两个口径的默认散布半角都收到 **0.3°**（`simulation_assumptions.projectile_spread_half_angle_deg`，17mm 与 42mm 同值）：10 m 内仍落在 125 mm 装甲板轮廓里，15 m 才明显扩散，中距离命中不再靠运气。战场设置仍可按口径覆盖（0–100°），引擎会把覆盖值写进回放校验；`simulation/src/mechanism_tests.rs` 的两个散布测试分别锁住「射线不越出锥角」与「近距近似全中、远距开始掉命中」。

**超级电容与功率**：引擎只接受「功率预算」，不认「一键放电」——`power` 字段（0–200 W）抬高预算后，超过整车功率上限的那部分由超电补足。超电并不是无损的：额定 24 V × 12 A 的输出里只有 **60%** 能送到电机，另外 **40% 在变换与内阻上损耗掉**（`SUPERCAP_LOSS = 0.40`），所以电容放电是「1/0.6 ≈ 1.67 倍」于实际多出来的电机功率，`cap_out = max(0, 电机功率 − 上限) / 0.6`；这部分损耗**不记入底盘功率**，`power_w` 仍只统计真正作用在底盘上的功率（`power_w = 电机功率 − 有用的超电功率 + 回充`），所以功率弧不会因为超电而虚高。按住 C 只有在真正加速、自旋、顶墙时才会把 1800 J 花出去，站着不动只走电池；测试中按住 W + C 加速时，超电每秒掉掉的电量约为「多出上限的功率」的 1.67 倍，松开后按 35 W 的上限回充。

**完全控制的前哨站增益点**和补给区一样能补给自己：站上己方**完全控制**的前哨站增益点（`positions[].controller` 为自己且 `control == "full"`）后，可以按同样的原价买弹，并获得补给区回血速率 **50%** 的治疗（开局 4 分钟后脱战时按脱战档位的 50%）；同时它会解除「虚弱」及其对应的无敌状态，和补给区、基地增益点一致。前哨站被重建后按**实际颜色**判定归属，所以红方前哨站重建为蓝方后，只有蓝方能在那里补给。

**空中机器人不能手动驾驶。** 2027 的空中机器人系统与 2026 的无人机由引擎的自动飞行与撞击逻辑控制，驾驶面板中不会列出它们，接口也会拒绝这类接管请求。

**小陀螺自旋按 `yaw_rate` 通道实现**（与参考模拟器一致的做法）：按住 Shift 时浏览器在下发的动作里加 `yaw_rate`（rad/s）与 `yaw_boost`（0–1 的偏航力矩爆发），引擎的偏航力矩控制器把底盘角速度拉到该目标值，云台继续按世界坐标咬住你的瞄准，所以车体在转、准星不动。目标转速取「引擎 ±12 rad/s 上限」与「该机型云台偏航转速 ×1.7」中较小者，`yaw_boost` 让偏航力矩超过额定值——没有它，额定力矩把自旋卡在 4–5 rad/s，这也是实测「驾驶自旋 ≈ 额定两倍」的来源（重型 3.76→8.98、麦轮步兵 4.55→9.74、轮足步兵 5.00→10.35 rad/s）。策略不下发 `yaw_boost`，所以电脑的自旋完全不变，`simulation/src/spin_tests.rs` 把这两条都锁住了。`yaw_rate` 会覆盖 `heading`，所以自旋时 A / D 变成选方向、不再横移，W / S 依旧驱动底盘，可以边走边转；按住 C 时目标转速直接顶到 12 rad/s。

**底盘正方向跟随云台正方向。** 云台与底盘各有自己的正方向：驾驶时浏览器每 50 ms 把云台的世界朝向作为 `heading` 下发，引擎的偏航控制器把车体转向该方向，云台同时继续咬住世界瞄准点。所以「往前开」永远是往你看的方向开，A / D 平移时车头也不会为了「面向运动方向」而甩动；小陀螺时 `yaw_rate` 覆盖 `heading`，车体才脱离云台自由旋转。

**轮足跳跃用引擎自己的腿推力。** 空格按下后浏览器先发 `leg_height` 把腿压到最短蓄力 0.2 s，再把 `jump` 交给引擎：双腿以 (1 + 推力系数×力度)×重力伸腿 0.16 s，离地后自动收腿；落回地面后再压腿 0.5 s 缓冲。力度取 0.5（额定的一半），抬高约 0.4–0.5 m，仍能越过 0.2 m 台阶；腾空期间浏览器把 `leg_height` 锁在标称腿长，落点姿态更稳。阵亡时跳跃状态机自动归零，不会卡在「腾空」。

**轮足登阶模式（F）。** 按住 F 时引擎从**机身外缘**（`radius`，不小于 0.22 m）向外 0.02 / 0.16 / 0.32 m 三处探测台阶高度：只要有一个落差落在 0.04 m 到该机型 `step_climb_m`（+1 cm 容差）之间，就进入一次登阶——腿伸出到最大行程并保持整个登阶过程，随后车体进入 1.3 s 的**搬运伺服**：先把机身抬到踏面之上（上升 0.6 m/s，第一段先升、第二段再前进，避免机身贴着台阶立面时被顶翻），以 1.1 m/s 沿车头方向把轮子送上踏面，再收腿。登阶期间**不触发跳跃推力**、并施加扶正力矩压住俯仰，所以不会再出现「上到一半翻过去」；一次尝试后还会等 0.35 s 让车身在踏面上停稳再判断下一级，避免了以前「上去之后原地抽动」的连环登阶。另外，跨在台阶边缘、两轮都探不到地面时，引擎会把「车身正下方 0.3 m 内最高的地面」当成支撑，驱动不会因为失去抓地力而卡死。`step_climb_m` 为 0 的型号（折叠麦轮步兵等）接口会直接拒绝 `climb`。实测 RMUC 2027 制高点台阶（第一级立面 0.4 m，之后每级 0.2 m）可以按住 F 连续登上去，机体全程保持直立，单次登阶的离地峰值明显低于一次完整跳跃。

**驾驶时的功率预算。** 平动与小陀螺都按该机型自己的功率预算执行（`power_limit`），不再额外加超电；只有按住 C 时才把预算抬到 200 W，超出上限的部分由超级电容补（并且按 40% 损耗折算放电量），所以超电只在你主动按下时才会掉。电容见底后底盘自然回落到自己的上限，和策略用超电的规则完全一致。

接管只覆盖你驾驶的那一台：同一时刻**策略进程仍在决策**，其余机器人照常按策略行动，比赛记录、回放与 Elo 判定都不受影响。浏览器以 20 Hz 发送操作，服务端在每次物理步进前用这些操作替换该机器人的策略动作。接管是「粘滞」的：短暂网络抖动（0.35 秒无操作）只让机器人刹车，不会交回策略；连续 2.5 秒没有操作（切走标签页、断网）才自动交还，避免策略在你驾驶时插手。被接管的机器人只把炮塔与炮管从画面里去掉，车体照常绘制。

驾驶时比赛速度会被调回 1×，全局快捷键（F 全屏、空格暂停、1–5 切镜头）暂时让给驾驶操作。回放中不能接管。

**局内背景音乐。** 倒计时的「5」一出现就进入局内音乐：先完整播一遍你安装的 `match-theme.m4a` / `.mp3`，放完接着循环仓库自带的 `summoning-glory.m4a|mp3`；没装文件时直接从老曲开始循环，不会静音。5-4-3-2-1 的报数只是叠在音乐上的蜂鸣。槽位、交接规则与格式兜底见上文「换成自己的音乐」。

**渲染开销。** 第一视角与广播共用一套场景，但会按模式调整开销：广播阴影固定 30 Hz 的旧设定已降到 12 Hz（阴影贴图也从 2048² 降到 1024²），画布像素比上限从 1.6 降到广播 1.3 / 驾驶 1.2，并在此基础上按实测帧时间在 0.8–上限之间自适应调整分辨率；驾驶时还会跳过 R3F 每次鼠标移动都要做的整场景射线拾取。

驾驶时的两处大头已经改掉：世界坐标里的血条/机构提示是 drei 的 `Html` 覆盖层，每帧都要更新 DOM，驾驶时改为**直接卸载**（不是隐藏），一场比赛里少掉十几个每帧重排的节点；场景树（`ArenaScene`）改为按「战场 + 阵容 + 镜头模式」记忆化，20 Hz 的帧快照不再触发整棵 React 树重建，只让渲染循环从 `feed` 读取位置。React 侧的帧状态也从 20 Hz 降到约 11 Hz（比赛、暂停、状态变化仍然立即渲染）。实测同一台机器上驾驶视角从 ~50 FPS 提升到 ~138 FPS（p50 帧时间 20.8 ms → 6.9 ms）。

**帧时间优先的三处改动。** 第一，**阴影刷新率跟着帧时间走**：阴影通道要把每个投影体（十二台机体加整座场馆）重画一遍，是最贵的固定开销，因此基准是广播 6 Hz / 驾驶 4 Hz，一旦实测帧时间超过 26 ms 就逐级降到 1 Hz，恢复到 16 ms 以内再逐级升回来；同时把包围球半径小于 16 cm 的零件（螺栓、相机、灯条、装甲边缘）从投影体集合里剔除，它们的影子根本看不见，却各占一次绘制。第二，**着色器预热**改为比赛一开始就用 `renderer.compileAsync` 在并行着色器编译器上编译整棵树（原来是首帧现编，恰好落在开赛那一刻掉一秒帧）。第三，**快照瘦身**：一帧里 `arena / robot_models / rulebook_rules / simulation_assumptions` 这四块是整场比赛不变的静态数据（约占一帧的 55%），现在每条战绩流只在换局时发一次 `static` 消息，之后的快照只带动态部分——实测单条快照从 ~115 KB 降到 ~44 KB，10 Hz 下每秒流量从约 1.9 MB 降到约 0.47 MB。

**鼠标捕获。** 桌面客户端里点画面即进入指针锁定（Pointer Lock），可以无限转动。桌面进程的 Electron 权限处理器显式放行 `pointerLock`，进入驾驶后系统光标会被隐藏并锁定，鼠标只提供相对位移，不会跑到窗口边缘或离开战场；画面中心固定的准星就是此时的鼠标位置。部分宿主（VS Code 内置浏览器、iframe 预览）**直接禁止指针锁定**，这时会提示「此环境不允许锁定鼠标」，并把光标整页隐藏：视角仍然跟随鼠标位移转动，只是指针移出窗口后会停止。需要完整的锁定手感请用桌面版（`python scripts/project.py desktop`）。

## 回放与录像：用途不同

| 方式 | 保存什么 | 之后可以做什么 |
| --- | --- | --- |
| 数据回放 | 帧、事件与比赛元数据 | 暂停、拖动时间线、换镜头、查看状态 |
| 视频录像 | 当时选定镜头和界面的画面与音轨 | 在播放器中观看和分享 |
| 数值重演校验 | 用记录的动作重新运行匹配引擎 | 检查重演结果，需要相同规则与仿真构建 |

在“比赛与回放”中选择记录可加载、导出或删除，也可以导入本地回放文件。删除数据前请保留想长期保存的导出副本。当前 v4 回放复用静态场景数据，桌面包保留历史素材与 v2 引擎用于兼容。

源码环境中可执行：

```sh
uv run python -m rmuc_arena verify-replay path/to/match.json
```

**能够播放旧回放，不等于能用当前引擎通过数值重演。** 2026 回放也不会因为你当前选择 2027 而更换比赛规则。

## 流畅度：每帧的钱花在哪里 {#performance}

广播画面是 three.js 实时渲染 + 9 Hz 的 React 快照刷新，所以"卡"通常来自两处之一：**每帧的绘制次数**，或**快照之间的插值**。两者都可以在浏览器控制台里直接量：

```js
arenaRender        // {calls, triangles, meshes, shadowCasters, materials, dpr, shadowRate, eye}
arenaCensus()      // 按最近命名祖先 / 网格名统计：谁占了几百次 draw call
arenaScene         // 场景根节点，配合 scene.traverse 做临时实验
arenaDiagnostics() // 含 pace（实测快照间隔）、prematch、audio、reel 等
```

已做的两件事：

- **阴影投射体按半径裁剪。** 以前每个网格都强制投影，一个底座就有 100 多个投射体，每次阴影刷新都是全额重画。现在只有 BoundingSphere 半径够大的部件投影（机器人 0.16 m、场景 0.45 m 起），实测投射体 **96 → 33**。
- **按关节烘焙颜色与表面参数。** 机型资产几乎每个零件一个材质，按材质合并几乎没有效果。改为把每个零件的**颜色、粗糙度、金属度**烘进顶点属性（`aSurface`，由 `rigidMeshes.ts` 里的着色器注入读取），再在**每个可动关节内**合并：车体、云台、枪管、每个轮子、每条腿节各剩一两次 draw call，而引擎驱动的关节节点本身不动。实测机器人网格 **120 → 37、87 → 23~26**，整场 **calls 1055 → 736、meshes 1242 → 891**，p95 帧时间 **13.9 ms → 7.1 ms**。新增可动节点必须写进 `ROBOT_JOINT`（`rigidMeshes.ts`），否则它的零件会被烘进上一个关节。

**插值跟着实测节奏走。** 引擎名义上是 20 Hz，但一次策略决策可能占住 200 ms，实际快照间隔常在 80–100 ms。过去按写死的 50 ms 插值，每个周期最后一段机器人是**完全静止**的（看起来就是一顿一顿）。现在客户端平滑统计真实到达间隔（`arenaDiagnostics().pace`），按它插值，并允许把上一步动作多带 30 % 来盖住偶发的 200 ms 停顿：实测冻结帧 **12 % → 7 %**。

还剩的优化路径（按收益排序）：

1. **服务端步进被策略调用挡住**：`battle.step()` 里同步等策略决策，直接把仿真拉到 11 Hz，比赛时钟也会跟着变慢。把策略调用移出步进循环是最根本的一条。
2. **底座 / 前哨站 / 基地的阵营发光件**：这些零件用 `Team*` 材质，驾驶座舱会逐帧改它们的自发光，所以现在不能合并（两个底座仍各占 61 次 draw call）。把它们也做成顶点属性 + 实例化着色器是下一步。
3. **场地标记与能量机关圆环**：`Zone` 每个区域 2–4 个网格、逐帧改颜色，改成 InstancedMesh + 实例颜色可以一次画完。
4. **炮镜双渲染**：开镜时整场景要渲染两遍（先渲进贴图再放大），这是第一人称最贵的一帧。

## 一个有效的复盘顺序

1. 先确认这局的赛季、对手、阵容和种子，避免拿不同条件直接比较。
2. 2027 先看哪一段控制度开始拉开，再回到当时的控制点。
3. 检查丢点的机器人是否缺弹、过热、阵亡、视野受阻或路线受限。
4. 只改一个明确问题，重新练习并提交新版本，再与相同条件下的旧版本比较。
