# 训练、对战与回放

Arena-1 的一次完整使用流程是：**选赛季 → 看懂或开发策略 → 选择阵容对战 → 看结果与回放 → 修改策略再试**。2027 与 2026 共用这些功能，阵容数量与比赛规则随赛季变化。

[![策略开发与比赛流程：创建任务、开发练习、提交入库、对战复盘、再次迭代](/media/strategy-workflow.svg)](/media/strategy-workflow.svg)

*Agent 在开发阶段写代码；进入比赛后，由提交的 Python 程序每秒决策 10 次。*

## 录制 MP4 视频

有两种录法，进度都显示在窗口右下角的录像面板里：

- **整场录制**：开赛前勾选「自动录制整场 MP4」。从赛前阵容介绍录到 MVP 结算：MVP 展示 8 秒后自动结束；提前点「回到战场」「返回数据面板」等按钮也会在那一刻结束。录像随后在后台转码并保存到该场比赛，可在「比赛与回放」中播放或下载。
- **录制片段**：在对战页点击「录制片段」，结束时点击「停止并保存」。实时比赛和数据回放都可录，可先选好镜头和播放速度；停止后自动转成 MP4 并下载。

录制期间请停留在对战页面，画面直接取自 3D 场景。停止后不用等待：面板依次显示「上传录像 → 转码 MP4 → 保存」的进度与剩余时间，期间可以继续操作或切换页面，只是不要关闭窗口。
视频包含比分、倒计时、结果叠层与合成音轨，1920 × 1080、30 FPS，H.264 视频加 AAC 音频。

MP4 在本机转码，不上传到外部服务；桌面安装包自带转码组件。缺少转码组件时，片段直接保存为 WebM，整场录制不可用。
保存失败时面板保留原始录像，可以「重试」「下载原始 WebM」或「丢弃」。单段录像上限为 1 GiB、1 小时。

## RM 对战：先比较策略

RM 对战要求双方使用同一赛季的完整阵容。2027 固定五个位置，2026 固定六个位置；红蓝各自使用策略开发时锁定的合规型号，双方硬件可以不同。

![2027 出战机库中的机器人与合规提示](/media/rmuc2027-lineup.jpg)

*型号名称说明硬件，位置编号说明它在队内的身份。型号不合规时，界面会解释原因。*

建议第一次保留默认阵容和示例策略。之后每次实验只改一个因素，例如保持阵容、对手与种子相同，只改步兵的抢点路线。比赛中的弹丸、碰撞、血量、资源与判定均由引擎处理，策略不能直接修改规则结果。

如果阵容改变，已有全队策略可能不再适用。只有与当前阵容匹配的提交才可用于对应 RM 对战，必要时先创建新的开发任务。

## 自由对战：按型号与策略组合 {#free-battle}

自由对战允许两方使用不同的数量、重复型号与战术组合。每张可选策略卡对应一个机器人型号和一种打法；你可以为同型号搭配不同策略，也可以把常用组合保存为卡组。

![2027 自由对战的型号、战术与两方卡组](/media/rmuc2027-free-battle.jpg)

*先选当前赛季合规的型号，再选择每次部署使用的策略。2027 每方最多一套空中机器人系统。*

一个可操作的对照实验：红方使用抢点步兵，蓝方使用守点步兵，先从少量机器人开始，观察路线、视野和火力，再逐步加入其他兵种。

| 控制方式 | 怎样运行 | 适合什么实验 |
| --- | --- | --- |
| 独立控制 | 每次部署使用各自的单机策略，内部状态分开 | 研究重复型号、局部协作、同型号不同打法 |
| Team 全队控制 | 一份全队策略读取实际部署并控制本方所有机器人 | 研究集中调度与不对称阵容 |

两种方式可以分配给不同队伍。选择全队控制时，策略也应能识别实际阵容，不能假设部署编号一定等于型号编号。自由对战改变的是出战组合，不会取消赛季规则与型号合规要求。

## 训练：生成一次有期限的开发任务

训练页提供四种方式：

| 模式 | 你开发什么 | 适合谁 |
| --- | --- | --- |
| 全队统筹 | 一份控制全队的程序，2027 五台 / 2026 六台 | 想研究完整战术，或第一次开发 |
| 单机专精 | 固定位置的一份程序，之后与其他位置组队 | 只想专注一个兵种或技能 |
| 多机协同 | 每个位置一份程序，2027 五份 / 2026 六份 | 研究消息、分工与独立决策 |
| 自由适配 | 某型号可重复部署的单机程序 | 自由对战、重复型号与变化阵容 |

![训练页中的开发方式、任务名称和开发计时](/media/training.jpg)

*这张历史截图来自 2026，旧版“六机协同”在当前界面中为“多机协同”。2027 任务生成五个位置的资料；请先在当前训练页选择赛季。*

选择赛季、模式、必要的阵容和开发时间后，点击创建任务。**计时从创建时开始**，包含阅读、编码、练习和提交；截止前最后一次成功提交的版本成为参赛版本。创建后显示的 `AGENT_TASK.md` 路径就是交给 Agent 的入口。

从命令行创建工作区时，创建和启动计时是两个步骤，不能照搬训练页的自动计时假设。详细命令见[策略开发](./strategies)。

## 策略库：先看它怎么打

策略库使用 `showcase.json` 战术卡解释每份策略的打法，提供生成者、控制模式、战术与标签等筛选，以及风格雷达、比赛阶段、地图路线和关键决策。

![战术卡内容示意：身份、风格、阶段、地图与关键决策](/media/strategy-card-guide.svg)

*展示来自策略作者填写的战术卡，应结合实际回放判断；“进攻强”“善于协同”等描述不等于胜率保证。*

预置策略按型号与战术集中收纳，默认可以折叠浏览。上传自己的策略时，需要提供代码和合格的展示文件；只改说明不会改变代码版本和 Elo。

策略库默认按 Elo 从高到低排列（未上榜的排在后面），也可以切换为最新或名称。每张卡片都标出上传者的 GitHub 主页：内置与在线策略由 [RM-Arena](https://github.com/RM-Arena) 发布；自己上传时可在上传向导中填写 GitHub 用户名或主页链接，之后也能在「编辑分类」里补充。

## 机器人模型与自定义外观

在策略库的“机器人模型”页查看硬件或上传 `.glb` 外观，再在开赛前“机器人外观”中选用。

**外观与性能是两回事。** 换一辆看起来更大的车，并不会增加血量、碰撞尺寸、速度或火力；比赛仍使用原型号的硬件参数与规则。真正比较硬件能力时，应切换出战型号并检查赛季合规。

## 观战：把动作与资源联系起来

比赛包括赛前自检、倒计时、实时场景、击毁播报与赛后结果。观战时可以切换镜头、跟随机器人、暂停和倍速，也可以查看金币、血量、弹药、热量与机构进度。

场上那几条血条（机体、基地、前哨站）和伤害飘字是**朝向镜头的广告牌**，在渲染这一帧的绘制阶段统一对齐当前镜头，所以跟随镜头绕着机体转、机体自己高速转向时，血条始终正对画面，不会跟着车体一起偏过去。**大小也在同一遍里算**：广告牌按「画面上保持固定像素宽度」反推世界尺寸，这一步同样读取绘制前那一次镜头姿态，所以跟随镜头一点点推近时，血条是一帧一帧均匀放大的，不会先用上一帧的距离缩放、再在一个画面上抖一下。

2027 尤其要把三件事一起看：**控制度变化、前哨控制状态、基地保护**。某台机器人暂时没有射击，也可能在维持卡片、等待冷却、装配科技或安装发射机构。

顶部每张机体卡下方会实时列出它当前的增益与减益：圆形图标 + **最终数值**（防御是盾牌、易伤是破碎盾牌、热量冷却是温度计，另有攻击、底盘功率、无敌、虚弱、过热、锁定）。百分比都是引擎当帧的最终值，同类增益已取最大值：防御 `50%` 表示受到的伤害 ×0.5，易伤 `100%` 表示 ×2；热量冷却显示的是「当前冷却速率 ÷ 基础速率」（例如 40→115 /秒 显示 `288%`），而不是那一项加成本身。驾驶时同一组图标也会出现在第一人称画面右下角。

赛后面板、MVP 与伤害统计有助于复盘，但不能替代规则判胜；排行榜 Elo 按策略版本累计，手动结束和含策略错误等不满足计分条件的比赛不会更新评分。

### 赛后流程：数据面板 → 对局高光 → MVP {#highlights}

一场比赛结束后按 **胜利演出 → 数据面板 → 对局高光 → MVP 结算 → 回到战场** 走完，每一步都可以手动跳过：

![赛后数据面板：胜负判定、基地与前哨站、累计控制度和双方关键数据](/media/rmuc2027-results.jpg)

![对局高光：从本场回放剪出的片段，下方标出事件、机体和本段伤害](/media/rmuc2027-highlight.jpg)

- **数据面板**放在高光之前，出厂时播放仓库自带的 `results-theme.m4a`（→ `.mp3`），和赛前铺垫听上去是同一场演出；想换成自己的曲子，放一个 `results-custom.m4a` / `.mp3` 就行。
- **对局高光**紧接着数据面板：放完（或跳过）就进入 **MVP 结算**，所以一场比赛的收尾是"先看比赛怎么赢的，再看是谁赢的"。
- **MVP 结算**播放仓库自带的 `mvp-theme.m4a`（→ `.mp3`；两者都解不出来时才退到 `victory.m4a`），不会静音。**这首曲子每场只放一次**：不循环，重复渲染或从数据面板再回到 MVP 也不会重头再播。卡片上「返回数据面板」回到面板（不会再自动跳转），「回到战场」结束整个赛后流程。
- **对局高光放的是这场比赛的录像本身**，不是重新摆拍的卡片：片段从裁判事件流里剪出（**共 3 段、每段 5 秒**），排序偏向「能不能说明这局怎么赢」而不是单纯的人头数：机器人对前哨站/基地装甲打出的成段结构伤害、无人机连续撞甲 > 本局输出最高机体的峰值窗口（标题「输出王」，说明总伤害里多少打在机器人、多少打在建筑）> 多杀（8 秒内同一台机的连续击毁算一段，标题为「双杀 / 三连击 / 四连击」）> 击毁前哨站或打穿基地装甲 > 能量机关激活与 3 / 4 级装配 > 连续火力压制；**单杀只在前面的素材凑不满三段时兜底**。然后**由服务端从裁判的逐帧日志里只切出这些窗口**（整场回放有几百 MB，整份加载会把浏览器主线程卡死几秒），每段自带 **1.5 秒走弹**再播 5 秒，所以能看到弹道抵达、装甲板爆火的真实过程。切片通常 1～2 秒，期间画面显示「正在从本场回放中剪出高光片段…」。播放时镜头先切到该段主角机体跟随，约 2.2 秒后再切到承受伤害的那台敌方机体：活着的承受单位进入第一视角，已被击毁的则保持跟随镜头，保证「输出单位」和「被输出单位」两个视角都交代清楚；无人机段会直接跟随执行撞击的那一架小无人机，而不是停在机库上。跟随模式里选中空中机器人（机库）不会跟拍机库本体，而是高亮它的全部无人机并自动跟随领飞的一架，也可以在下拉框或战场上直接点选单个无人机单独跟随。画面上只叠一层广播式 HUD：左上角 `HIGHLIGHT 01/03`、当前是输出视角还是承受视角，以及比赛时钟，左下角下三分之一（标题、说明、主角、结构/峰值/本段伤害、击毁、进度点与 5 秒进度条），右下角「跳过高光」。全部放完自动进入 MVP，随时也能跳过。所有片段共用同一条背景音乐：从第一段起一直连着放，切到下一段（或取消切片等待）都不会从头重来。
- 只有当这场比赛**的逐帧数据已经不在内存里**（例如切到回放、重启服务后）或**根本没有可剪的时刻**时才退回原来的卡片版（整机渲染图、被击毁机体卡片、进度点）；完全没素材时如实提示「本局没有留下可用的高光素材」，4 秒后自动进入 MVP 结算，绝不凭空补镜头、也不会把人卡在一张空白的战场上。

**换成自己的音乐。** 每个提示位的主题曲都是**仓库自带的项目资产**（`<cue>-theme.m4a`，同一录音再配一份 `.mp3`），开箱即有声；想换成自己的曲子，把文件放进**本机覆盖槽** `<cue>-custom.m4a`（其次 `.mp3`）即可——它排在出厂文件之前，**放文件就行，不必覆盖仓库里的素材，也不用改代码**，刷新页面生效，也不会被提交进仓库：

| 时刻 | cue | 出厂文件（项目资产） | 覆盖槽（仅本机） |
| --- | --- | --- | --- |
| 倒计时「5」起播，**先完整播一遍** | `match` | `match-theme.m4a`（→ `.mp3`） | `match-custom.m4a` / `.mp3` |
| 那首播完之后（约 4 分钟起）**循环的**是老曲 | `match_alt` | `summoning-glory.m4a`（→ `.mp3`） | — |
| 赛前过场 / 选边（RM 对战） | `pick` | `pick-theme.m4a`（→ `.mp3`） | `pick-custom.m4a` / `.mp3` |
| 赛后数据面板 | `results` | `results-theme.m4a`（→ `.mp3`） | `results-custom.m4a` / `.mp3` |
| MVP 结算 | `mvp` | `mvp-theme.m4a`（→ `.mp3`，再退 `victory.m4a`） | `mvp-custom.m4a` / `.mp3` |
| 对局高光 | `highlight` | `highlight-theme.m4a`（→ `.mp3`） | `highlight-custom.m4a` / `.mp3`，或沿用旧的 `highlight.m4a` / `.mp3` |
| 首页与大厅 | `home` / `lobby` | `arena-theme.m4a`（→ `.mp3`，原创合成，见 `assets/audio/compose_score.py`） | — |

局内音乐是**一首开场 + 一首循环**：倒计时出现「5」（视为已进入局中）先用出厂的开场曲 `match-theme.*` **从头完整播一遍**（不循环），这一遍放完就自动接到 `summoning-glory.m4a|mp3`（`match_alt`）并**一直循环到本局结束**——开场是新的比赛主题，之后的循环是老版 Summoning Glory。每开一局都按这个顺序重来（回放不占这次开场，直接整局用老曲）。**同一局里怎么改倍率都不会换曲、也不会从头重放**；第一首还没放完就暂停 / 切倍率，回来接着放，放完才交接。只有这两个文件都解不出来时才直接从老曲开始循环，不会静音。`pick` 接管**整个赛前过场**：过场动画一出现就换成准备阶段的曲子，选边 / 选机体就叠在它上面，一直到倒计时才交给局内曲（自由对战仍用自己的过场曲，只有人在选边时才切到这首）。赛后关掉结算、回到「准备下一场」的布置界面时**不放背景音乐**（数据面板那首只属于结算），要等再开一场、进入过场 / 选边时才重新起乐。同一首曲子都同时提供 `.m4a`（AAC，体积更小）和 `.mp3`（保证在不带 AAC 解码的浏览器——Chromium 定制版、VS Code 预览、桌面壳——里也能出声），播放器会按 m4a → mp3 的顺序挑第一个能解码的文件。

**响度与切换。** 每首曲子解码后都会测量门限 RMS 响度（400 ms 分块，剔除静音与弱段），再把整首曲子缩放到同一个目标电平（约 −10 dBFS），所以赛前、局内、赛后数据、MVP、高光和本机替换的 `-custom` 曲目（无论母带偏响还是偏轻）听上去一样响，包括 MVP 在内没有任何提示位额外加高。切提示位时旧曲继续播放，新曲面世后两者约 1.4 秒交叉淡入淡出，不会突然变响、不会先静音再起乐。停乐、关声音也走同一套渐变。

一条命令就够（文件放哪都行，有 ffmpeg 会自动抽掉视频轨、转成 m4a + mp3；没有 ffmpeg 就把现成的 mp3 / m4a 复制过去）。它写的是本机覆盖槽 `<slot>-custom.*`，不会改动仓库里的主题曲：

```bash
python scripts/install_music.py "D:/music/我的曲子.mp3" --slot match
python scripts/install_music.py "D:/music/highlights.mp3" --slot highlight
python scripts/install_music.py "D:/music/interlude.mp3" --slot results
python scripts/install_music.py "D:/music/mvp.mp3" --slot mvp
```

覆盖槽文件不存在时，浏览器会先请求一次并拿到 404，再播放出厂主题曲——**控制台里这几条 404 是正常的**，代表提示位在探测本机覆盖文件。仓库里的主题曲是随项目发布的音频资产；覆盖槽请只放你有权使用的文件（自己的录音或已授权的音源），项目只负责把它接到对应时刻。


## 第一视角驾驶：比赛中手动接管一台机器人 {#pilot}

![第一视角驾驶：接管红方 3 号步兵，云台准星、弹量、热量与机体状态显示在画面上](/media/rmuc2027-pilot.jpg)

**赛前自检与倒计时。** 自检（阵容过场）阶段可以点「跳过」直接进入倒计时，但**5-4-3-2-1 一旦开始就不能跳过**：比赛时钟与局内主题曲都以它为准，服务端收到倒计时期间的跳过请求会直接拒绝（`400 倒计时不可跳过`），页面也不会显示跳过按钮，只留一行「比赛即将开始 · 倒计时不可跳过」。**过场每一段至少显示 2 秒**（开场 → 红方队卡 → 红方各机体 → 蓝方队卡 → 蓝方各机体 → 面交锋，共 `机体数 + 4` 段），所以自检时长是**自适应**的：选边 / 选机体花掉的时间会把自检时钟撑长（`POST /api/control {"command":"extend_prematch","seconds":n}`，时钟与对外公布的时长同时增加，已播的进度不受影响），倒计时相应顺延，而不是把某段卡片压缩成零点几秒；延长总量有上限（客户端累计 90 s、单次 30 s），不会因为有人离开而永远卡在赛前。局内主题曲从 **「5」出现的那一刻**就起播，而不是等比赛开始。

实时比赛进行时，直播画面**下方的播放控制条**里有一枚「驾驶菜单 P」按钮（全屏时在右下角控制条里变成图标按钮），它不再压在画面右上角的广播记分牌上，也可以直接按 **P** 开关面板。面板里只有一颗 **LINK START**：点下去以后面板**滑到画面右侧变成一条机库栏**（宽度自适应：`clamp(184px, min(22vw, 30vh), 300px)`，小窗 / 矮窗自动收窄并压紧行距，不会吃掉半个战场；栏体配色跟着当前浏览的阵营走——看红方是红色强调，看蓝方是蓝色强调）、镜头同时切到**俯视全场**，整块场地铺满画面（相机距离由场地尺寸与画布宽高比算出，取能完整框住 28 × 15 m 的距离再拉远 25 %，即场地只占画面的 **80 %**，屏幕上方那片广播记分牌就不会压住场地远端；屏幕上方就是场地远端、与小地图同向），鼠标靠近哪台机体，指针旁就浮出它的详细卡片（型号、血量、底盘功率、热量上限、单发伤害、机动速度、整机质量与底盘特性）——**镜头还会沿视线俯冲到这台机体上**，把它放到画面正中并放大到约占画面高度 30 %，指针移开就平滑拉回全场俯视；卡片固定贴在场地左下角，不会挡住正在被放大的机体。点一下那台机体——或直接点右侧机库栏里的条目——会弹出「建立神经连接？」确认页，确认后镜头**一路动态推进到第一人称**，键盘和鼠标接管这一台；点「返回」则原路收回原来的镜头模式：

**座舱配色随阵营。** 一旦接管某台机体，整块驾驶 UI 的强调色就跟着这台机体所属阵营走：接管红方时准星、弹药读数、HP / EXP / 缓冲 / 超电 条、小陀螺与超电提示、P 面板、购买与装配面板、机体卡上的 **P1** 徽标全部转为红色系（并加一圈极淡的红色边缘辉光），接管蓝方则整体转为蓝色系。这样一眼就能确认"我现在在替谁打"，也能避免在混乱的交火里误判阵营。**只影响驾驶时的座舱**：赛前选边简报、机体选择卡片、广播 HUD 仍然使用中性的仪表青，因为那时还没有"我的阵营"。

**基地受损会降低图传清晰度。** 2027 的 5.6.1 后勤系数 `λ = 1 − 己方基地已损失血量 / 20000` 同样作用于选手端：己方基地掉血后，第一人称画面按 λ² 的像素量降采样、再由浏览器双线性放大，基地越残画面越糊。**这只影响第一人称图传**：自由 / 俯视 / 跟随 / 环绕等第三人称镜头、导播画面，以及重型取矿与喂核心时的第三人称跟随视角都保持全清晰度；准星、血量读数、购买与装配面板这些座舱 UI 也不属于图传画面，同样不受影响。复活读条、补给区回血、远程兑换回血与多机通信带宽按表 5-19 随 λ 变化。

**开局选人与鼠标时机。** 点「开始对战」**直接进入战场选人**（不再弹询问窗），赛前自检阶段由镜头接管——先以**斜 45° 俯瞰全场**（距离按画布宽高比自动拉远，窄屏也能看到整块场地），场地的左右两半就是红/蓝半区：鼠标移到哪边，那半边地面就亮起队伍色、一条扫描光带沿半场推进、四个角的光柱升起、外沿竖起一道能量墙，指针处还有一枚贴地光环；**每半区上方浮着该方简报**（策略名、历史胜率、Elo、胜/负/平、上场机体数、比赛模式）：**没有卡片、没有边框**，就是一层浮在半场上空的文字（由场景按世界坐标定位，窗口再窄也不会把三份简报挤成一排），悬停的那一侧才会亮起，平时压暗。**看台高亮只在选边阶段生效**：选定阵营后观众席熄灭、镜头也不再为看台拉远，焦点回到己方启动区。**场地外一律算观众席**：看台、走道和场地四周的空地都点亮一道冷青色的发光框，指针停在那里时镜头会**向后拉远约 28 %**，让整排看台进入画面，同时**建模出来的阶梯看台与观众席本身也会亮起冷青色**（离开就淡回暗色），**看台上空还常驻一张「观众席 · 看台」简报**（标注视角自由、随时可接管、整局交给策略，同样无边框浮在看台上空），悬停时与看台一起点亮；底部提示「观众席已高亮 · 单击进入观众席」，点一下就是观众（也可以点底部中间的「观众席」按钮）。点一侧半区即选该方。镜头随即**缓动滑降**到该方**启动区的低角度三分之四视角**（约 1.2 s 的位置 / 视线双缓动，不是硬切；点「重新选边」也沿同一条曲线滑回 45° 全景）（整簇机体都在画面里），鼠标靠近哪台机体，镜头就像过场动画里的单机镜头一样**贴近那台机体**（同一套取景公式：按机体尺寸算距离、略高于机体、从车头斜前方看向车体中段），车体微微抬起并亮起队伍色光环，同时**直接复用赛前过场动画那套机器人镜头 UI 与特效**（闪光、扫光、瞄准框、逐条递增的数值条、底盘特性标签、策略 Agent 卡片、阵容进度点），点一下选定（选好还可以「重新选边」）。指针停住时目标被**锁定**，镜头推近不会因为屏幕投影变化而反复改判；只有指针明显移向另一台或离开该机体时才改判。整个选人**没有弹窗和列表**，场地和机体模型就是界面。**准备阶段不捕获鼠标**，指针留在浏览器里，可以继续点面板或跳过；倒计时结束、比赛真正开始后才自动把指针锁进画面（若浏览器因为没有用户手势而拒绝，会保留「鼠标未锁定 · 点击画面锁定」的提示）。被击毁时同样**立即释放鼠标**，方便点「立即复活」或等免费读条；只有复活后才会再次尝试捕获。场地内右键是自动瞄准，所以浏览器右键菜单、中键自动滚动、文字选择与原生拖拽都被拦截，按住右键只会锁定装甲板。你在驾驶哪台机器人，画面顶部那张机体卡上方的圆形徽标就不再是策略所属的 Agent，而是一个金色的 **P1**，标出这是人在开。

| 鼠标 | 转动云台：左右改变炮塔偏航，上下改变俯仰。指针在战场画面任意位置（HUD、地图、面板按钮以外的区域）都有效；点画面锁定鼠标后可无限转动 |
| 方向键 ← → ↑ ↓ | 不锁定鼠标时用键盘转云台（覆盖 HUD 遮挡的情况） |
| W / A / S / D | 沿炮口方向前后移动、左右平移；**底盘正方向默认跟随云台正方向**，所以机器人总是朝你看的方向开，平移时车头不会甩来甩去 |
| 左键 | 开火（仍受弹药与冷却限制）。**枪管热量保护**：驾驶端按 `/api/health` 里的规则弹丸热量（17mm 10 / 42mm 100）预留一整发再加 15% 余量，热量接近上限时自动停火；服务端每个 tick 还会用引擎的 `can_fire` 复核，迟到的开火请求同样会在越线前被丢弃，避免把热量推过上限触发枪管锁死。哨兵强化进攻姿态与重型装配弹按规则不加热 |
| 空格 | 轮足底盘：**跳跃**（下蹲蓄力 0.2 s → 起跳 → 落地缓冲 0.5 s，力度为额定的一半，抬高约 0.4–0.5 m，仍可越过 0.2 m 台阶与高地边缘）。其他底盘：开火 |
| F（按住） | **登阶模式**（轮足登阶型号，`step_climb_m > 0`）：抵住台阶时双腿先压后伸，把机体抬上台阶再收腿，连按同一路线即可一级一级登上制高点三级台阶。引擎从**机身外缘**（约 0.22–0.32 m 半径）往外 0.02 / 0.16 / 0.32 m 三处探测，只认 0.04 m 到该机型 `step_climb_m` 之间的落差，所以贴着台阶按也照样触发，而不会把它当成跳跃 |
| 右键（按住） | 自动瞄准：只锁定**第一人称视野内、12 m 以内、且从视线和枪口都不被墙体或平台挡住**的敌方装甲板（不是车体中心，机器人、前哨站和基地都算；前哨站按重建后的实际归属判定）。**超过 12 m 一律锁不上**——无论机器人还是前哨站/基地，避免隔着半个战场挂靶。可见性以**实际会被瞄准的那块装甲板**为准：机器人按底盘尺寸与姿态重建四面装甲板，前哨站/基地按朝向选板，再用**精确线段/包围盒求交**检查墙体（包括 0.15 m 薄墙）与地形，所以车体露出来、但装甲板被墙或高地挡住时不会锁定，**没被遮挡的那块永远优先**。锁定还以**当前炮塔/镜头实际朝向**为准，不拿鼠标目标角去锁画面外的板。视野里有多个可锁目标时，**先看谁的装甲板露得更多**：夹角相差不到约 4°（10 m 外正好是一两片装甲板的宽度）的几块板算「都在准星下」，这时按**装甲板实际暴露比例**决胜——把板面按 3 × 3 采样，逐点做遮挡判定，露得最多的一块胜出；夹角差超过这个带宽则仍由更靠准星的那块说话，准星压住的那块不会被远处更干净的板抢走。没有这一步时，一块从掩体后露出半截的板会跟旁边完整的一块打成平手，谁离准星近一像素就锁谁，主观上就是「老是锁到打不到的那块」。**锁定会保持**：已经挂上的装甲板只要还在视野里、还在 12 m 内，就不会被旁边略近一点的目标抢走——新目标必须比它明显更靠准星（约 4°/15% 的余量）或明显更暴露（暴露比例高出 15 %）才换锁，所以目标自旋、部分被掩体擦过时不会来回跳。目标选定后由服务端按引擎弹道解算炮塔角度与抬升，并显示锁定目标与距离。**10 m 内**同时使用完整的偏航和抬升解算；**超过 10 m** 仍解算俯仰，但只取解算值的 **80%**（比正常自瞄瞄准点低 20%），远距离不会再把准星抬到目标上方漂着。视角会平滑贴到炮塔角度上，松开右键不会跳回旧方向；右键永远不开火 |
| O | **购买弹药**（所有机器人，含重装）：在己方基地、补给区、制高点或**已完全控制的前哨站**打开购买窗口，用 −50 / −10 / −5 / −1 与 +1 / +5 / +10 / +50（42mm 为 −10 / −5 / −1 与 +1 / +5 / +10）调整数量，中间显示本单总发数，下方「确定 / 取消」。窗口打开时鼠标交还浏览器，确定或取消后重新锁定；按确定之后引擎按原价（17mm 10 发 / 10 金币、42mm 1 发 / 10 金币）按比例扣金币并立即补弹 |
| I（重装） | **重装的机械臂操作**：己方矿区里停在取矿位（取矿点外侧约 0.60 m，双臂重装 0.48 m）、车头大致正对取矿口时**按住 I** 取矿——对准能量单元 → 夹取 → 抬升 → 收入弹仓共四段，**全程按住 I**：一是这条请求要在每个仿真节拍都发出去（规则把「这一拍没发」当成松手，会立即取消），二是松手 / 开走 / 离区仍会中断。按住 I 可以边开边对准，进入可及范围后自动起夹；机械臂够不到约 3 秒后取消并提示重新对位。**取矿与装配都有一条带百分比的进度条**（在准星下方，蓝色是取矿、金色是装配），不再只有一行提示——从「显示进度」还是「一动不动」就能立刻分辨这一把是跑起来了还是被拒了。两个弹仓装满后可以再取**第 3 个**，它直接夹在**夹爪上**（镜下模型可见），松手也不会掉，跟着车开到兑矿台；其他位置**按 I** 打开**兑矿 / 装配难度**面板，选择 1–4 级并下达装配指令（详见下文「重装机器人：取矿与装配」） |
| J（重装） | **装备 42 mm 发射机构**：42 mm 已解锁后，停在己方工位（`workbench`）内**按住 J**，界面上会出现一条金色的「装配 42 mm 发射机构」进度条走到 100%（离开工位会中断、进度归零）；未解锁或已装好时按键只给一句提示，不会误触别的功能 |
| R（重装） | **吊射机械瞄具**：42 mm 装好后（`fitted` / `installed`）按 R，**镜筒会从炮侧翻到眼前**（0.26 s 的机械翻转，落位之后镜内再用 0.18 s 从 1× 平滑涨到 2.5×；关镜时先把放大退回 1×，镜筒再翻回炮侧，全过程没有硬切），不是全屏遮罩：**镜筒就是一个 3D 圆筒**（筒口一圈实体金属镜框，向外加宽、不挤占镜内视野，跟着视线一起摆）；**只有镜内（约屏高 58% 的圆形孔径）是 2.5× 放大**，并带一点正常镜片的桶形畸变与暗角，镜外保持 64° 正常倍率；**准星是 UI 叠加**而不是画在场景里——四段 SVG 发丝线（1 px 描边 + 一圈暗描边保证在亮墙 / 暗地上都看得见）加一个中心点，尺寸固定为屏高 58%，所以不随倍率放大、任何分辨率都是发丝细。镜下读出「吊射 · 2.5× 镜内放大 · 准星即落点 · 距离」。这是**平射精确弹道**：炮管仍保持正常的正俯角（4 m 约 −4°，12 m 约 12°，20 m 约 29°），服务端用 `sdk.lob_aim` 解出含阻力与继承速度的落点角，让弹丸正好落在准星压住的那一点——开镜后视线由驾驶员控制，炮口在下面独立解算。驾驶端把准星方向**射线命中的最近一个实体**的世界坐标发给服务端：先比敌方的基地 / 前哨站装甲板（射线与板面、板面范围求交），再比场上任何一个障碍物盒（墙、平台、台阶、装配台——按旋转包围盒做三轴裁剪，擦过顶沿就落在顶面上），最后才落到地形 / 地面。过去只测装甲板和地面，于是把准星压在射手与目标之间的墙上时，落点会被算到墙**后面**的地面上，和准星完全不是一回事。**扣扳机不会立刻出膛**：炮管要先按 `turret_pitch_rate_rad_s` 转到解算角，服务端在这之前一直压住这一发（界面显示「抬炮中，到位自动发射」），点一下也会等到到位才打。42 mm 平射最远约 21 m，超出时镜下提示「超出射程」且不发射；准星没压在落点上（天空 / 场外）同样不发射。再按 R 翻回；未装枪 / 非重装按键只给提示 |

第一视角镜头就是云台本身：眼睛装在枪口高度的 1.27 倍处（`FPV_EYE_LIFT`，比之前的 1.495 低 15%，更贴近枪线又仍然越过炮管），`yaw` 与 `pitch` 都直接取引擎帧里云台的角度（20 Hz 采样之间做插值，机器人模型的炮塔/枪管用同一个插值系数摆姿态），因此**视线俯仰 = 枪管俯仰**，准星和炮口不会再各指一边；旁观别人的第一视角时才改用缓动跟随。鼠标推动云台的**目标角**并受引擎云台转速限制，是否转动由引擎决定，不会出现「镜头飞了、炮口没跟上」。低头可以看到自己的车体：驾驶时只隐藏炮塔与炮管（眼睛就在它们里面），车体、轮腿与装甲照常绘制。

**第一人称中心读数。** 准星外是一圈枪管热量环：冷时浅灰，接近上限转黄再转红，枪管锁死时为深红；外圈那 60° 的白色圆弧标出车头相对视线的方位，开启小陀螺时会跟着底盘转动。外围三段圆弧依次是超级电容、血量与底盘功率。枪管过热锁死时战场画面直接变黑、只保留 HUD，中央提示「热量超限」，热量清零解锁后自动恢复。整块第一人称 HUD（准星、读数、左下状态栏、提示条）会随对战窗口大小**等比缩放**，小窗口不再出现与战场不成比例的大号图标；左下角状态栏与其余 HUD 使用同一缩放比例，等级、血量、缓冲能量、脱战计时、增益图标与六个机构指示灯都按这一比例绘制。左下角状态栏的缓冲能量是一条灰白进度条；底盘超功率断电时缓冲条右侧显示红色「底盘超限」，「底盘」角标同时变红，而「云台」「发射机构」仍保持供电。引擎这一 tick 施加的增益/减益（防御、攻击、冷却、锁枪等）以图标形式直接排在血条上方。

**重装机器人：取矿与装配（第一人称）。** 2027 的重装机器人前期不再只能交给策略：驾驶时靠近己方矿区（`red_resource` / `blue_resource`）**按住 I**，机械臂会走「对准能量单元 → 夹取 → 收入弹仓」的完整流程，最多携带 **3 个**能量单元——取矿位在取矿点外侧约一个臂长（单臂型号 0.60 m，双臂型号 0.48 m），车头要大致正对取矿口；按住 I 时可以先开车对准，进入可及范围并自动起夹，机械臂够不到的抓取会在约 3 秒后取消并在镜下提示重新对位，不会停在「对准取矿台 0%」。**这条请求每个仿真节拍都要发**：规则把「这一拍没带 `pick_unit`」当成松手并立刻取消，早先驾驶端每拍重新判定「是否停稳、是否在范围内」，只要车体漂几厘米就漏发一拍，取矿于是反复从 0 % 重来——表现就是「按了 I 有提示但永远不进动画」。现在一旦开始就按到结束（只有松手、开走、离区才会真正中断）。两个弹仓装满后，第三个直接**夹在夹爪上**（`unit_pickup.stage = carrying`，松手、开走、离开矿区都不会丢，模型中能看到它夹在爪上，机械臂把它举在立柱前方），到核心前插入时**先消耗夹爪里那个**，再去取弹仓；到场心的**兑矿台**（`assembly` 区）**按 I** 打开装配面板，面板按规则逐条列出四级状态——一级开局可做，此后每分钟解锁一级；每级必须先完成上一级；四级一场只能完成一次；一级需要 1 个能量单元、四级需要 2 个。四级那两枚核心必须在第一枚插入后的一个窗口内**连续插完**，这个窗口按规则里的插入 / 平移 / 旋转速度加上这一局实际的目标角换算，配置的 3 秒只是下限——否则目标角稍大一点（比如 45° 要 0.375 秒旋转，再加 1 秒插入、0.7 秒平移和 1.2 秒确认就已经超过 3 秒）就成了必超时的物理不可能，过去只有旋转角接近 0 的姿态能碰巧过。面板同时给出每一级的**首次 / 非首次收益**（等级、每 10 秒金币、25% / 50% 防御增益、等级上限、42 mm 解锁）。下达后由**机械臂自动完成**插入 / 抬升 / 翻转 / 旋转到目标角 / 确认这几个动作（驾驶端按引擎帧里的 `cores[].target_rotation` 与 `blocked_reason` 逐 tick 下发，人工不必同时操控五个轴），第一人称镜头会**跟着机械臂看核心**。**取矿与兑矿的机械臂耗时是原来的两倍。** 自动取矿 / 装配的关节响应速率降到常规的 **37.5%**（半速），四个取矿阶段的驻留时间同步加倍（0.4 / 0.7 / 0.6 / 0.8 s），核心的插入 / 平移 / 旋转 / 抬升 / 翻转速度也各自减半（`arm_insert_speed_mps` 0.1→0.05、`arm_translate_speed_mps` 0.15→0.075、`arm_rotate_speed_deg_s` 120→60、`arm_lift_speed_mps` 0.15→0.075、`arm_flip_speed_deg_s` 180→90）；**实测一次完整取矿由约 3.5 s 变为 7.05 s**。手动遥控与救援保持全速——那是驾驶员自己的手。够不到单元的判失败窗口也随臂速放宽到 8 s，否则半速下正常的「从收纳姿态起夹」会被误判为够不到。

**兑矿按钮点了没反应的原因已修。** 规则只在它自己的节拍（`tick % 2 == 0`）上读取指令，而面板上的一级到四级按钮是**一次性下发**——落在不被读取的那一拍就被静默丢弃，实测约一半的点击没有效果，看起来就像按钮坏了。现在按下等级后会**持续重发 4 秒**，直到引擎明确回答：`assembly_start` 表示机械臂接活（提示「N 级装配已开始」），`assembly_refused` 则说明原因（不在兑矿台上、没有能量单元、该级未解锁、需先完成上一级、四级本场只能用一次、已有装配进行中、核心已锁定、对方正在做四级装配需让行），并在座舱里弹出对应文字。拒绝事件按「队 + 等级 + 原因」**每秒最多一条**，重发不会刷屏。 **只要重装机器人站在己方兑矿台（`assembly` 区）的场交互模块卡上，它就处于无敌状态**：不必正在装配，也不消耗时间额度，被击毁前的保护时间用完也照样生效——打开装配面板时会显示「己方装配区内重装机器人处于无敌状态」。离开卡片（含 2 秒释放延迟）才恢复可被击穿；敌方装配区不提供保护。把机器人开到己方工位按住 **J** 就能装 42 mm，界面上有一条金色进度条（装配 42 mm 发射机构 · 百分比）走满为止，离开工位即中断——过去这一段只有一行文字提示，看不出到底在装还是被拒了。**安装本身整局任何时候都能做**；但**解锁是硬条件**：只有完成三级装配、或比赛进行到 300 − M/50 − 2N/3 秒之后，这台重装才打得出去（解锁前弹匣里有弹也扣不动扳机，首发射击才把机构从 `fitted` 定装成 `installed`）。**装好（以及开火后的 `installed` 状态）之后镜头立刻切到发射机构云台**，跟随炮管的 yaw / pitch，不再回到机械臂。尚未安装发射机构时，重装的第一人称视角就是**机械臂工位视角**：眼睛落在车体中线上、机械臂立柱前方一点，高度按重装自带的机械臂相机取（约 0.5 m，比发射机构云台的炮线低一半多），所以既能看清脚下与兑矿台，又不会把立柱顶在画面正中央。**留在第一人称的那些步骤里，视线沿大臂（升降臂 → 伸缩臂）的轴向走**，而不是跟着夹爪的姿态：夹爪自己的俯仰、滚转不会甩动画面，只有大臂抬起、伸出或收回时镜头才跟着转，所以整段取矿 / 装芯都能看到机械臂末端的动作。取矿或装配进行时，镜头会切成**和「跟随」模式一样的第三人称追车机位**（沿车头方向后退 4 m、抬高 4.4 m 俯视车体），能同时看清机械臂与大臂末端的动作；夹爪夹住第三个能量单元（`unit_pickup.stage = carrying`）或机器人离开取矿台之后，镜头**立刻回到第一人称**。进出这个机位、以及第一视角 ↔ 跟随 ↔ 广播之间的切换都是 0.5 秒缓动，不会硬切。平时（不在工作）看车头方向；视角取自与车体同一套插值姿态，不会在 20 Hz 采样之间抖动，也不会在机械臂视角与云台视角之间来回跳。装配各步的判定只要求**工具末端仍在核心上（位置 + 单元滚转）**，不再要求机械臂把工具轴线摆到某个绝对角度——倾斜核心抬升单元时腕部会顶到行程极限，过去正是这条判定把 3 / 4 级装配卡在「flipping」上。**装配的硬性规则现在逐条落地**：单元一旦进入核心就**锁定难度**（面板上四个等级的按钮全部置灰并写明原因），同一难度在成功前核心保持**相同位姿**；**每次装配成功后核心要重新初始化 5 秒**，期间面板显示剩余秒数、下单会被拒；确认开始后再去拉单元会被判「单元被取出」并**立即失败**（单元回到机器人弹仓）；连续 **15 秒**不在装配区交互模块卡上判失败并自动退出、核心立刻回收单元；重装被击毁时装配立即失败，核心保留单元 **15 秒**再回收（这 15 秒是给操作手脱离核心的窗口，模拟里被击毁的机体不能再驾驶，所以用来读提示）；核心没有避障，路径被别的机器人挡住会**过载警报 + 悬停**，让开后自动继续；单元可绕 Q 轴**顺/逆时针各转 90°**。**失败一定看得见**：驾驶端弹一条通知（写明原因与「核心 N 秒后回收能量单元」），装配面板里留一条红色失败条，面板上还有「取消装配 · 立刻回收能量单元」按钮，事件流同时记一条 `assembly_failed`。

**第一人称只显示自己和赛场态势。** 进入驾驶后保留对局正常的**顶部记分栏**（双方名称、基地/前哨血量、剩余时间、控制度与伤害、金币），唯一区别是对方机器人一侧的卡片保留正常版式，但**血量条只显示灰色占位**，弹药 / 机构读数、等级箭头与复活百分比都不公开（外观、名字与编号照常，便于认车）；窗口较窄时顶部记分栏会切到紧凑布局（只收起前哨站数字），但**机器人卡片与血条行始终保留**，不会因为窗口宽度而消失。**右下角保留观战那张战术小地图，但按驾驶员的视角过滤**：己方机体实时显示，对方的三个点只按 **2 Hz** 取样（位置是半秒前的一帧，散点照样能看出站位，却当不了实时雷达）；右侧数据面板与机体详情仍然关闭。视野中只保留贴住画面底边的左下角血量 / 等级经验 / 电容，画面中央的热量环与弹量，以及锁定目标提示。视角为 **64°**（比原先的 80° 收窄 20%，边缘不再把视线从准星上拉走）；广播镜头仍是 42°。

手感上：中心圆环保持 40% 透明度，但半径是原来的 4 倍（384 px 直径，短窗口自动缩到 300 / 220 px），弹量与热量挪到**圆环右侧**单独显示，不再压在准星上；鼠标灵敏度按 64° 视场等比缩放（同样手部位移转过的角度一致）；按住方向键 0.7 秒后转速线性提升到 2 倍，轻点微调、长按快转都跟手；每次输入（移动鼠标、按下**和松开**开火/移动键、按键）在无请求在途时会**立刻**下发一次；请求在途时到达的输入会在回包落地的那一刻补发（尾沿发送），最坏输入延迟从 50 ms 降到一次往返，松键即刹。驾驶时快照按 8 ms 轮询推送（观战仍是 25 ms），云台的新角度更快到达画面；转向指令、键盘转速与锁定跟随也都上调了 20%。复活时准星直接对齐新出生姿态的云台角，不会从阵亡位置扫回来。

**镜头跟手：指令每帧推进，回包只做校正。** 云台角原本只在 50 ms 的发送节拍上推进，而画面读的是引擎对这条指令的**回包**——回包只能跟着比赛快照到达（约 10–50 ms 一次），于是实测「按住右键转向」时有 **41% 的帧镜头完全没动**，随后一帧跳 15°。现在驾驶端用**每帧的动画循环**推进指令角（上限改成该型号云台自己的转速：指令跑得比云台快，误差只会越拉越大，最后一定要被拽回来，那正是那次跳变），画面直接读这条指令角，回包只以 6 s⁻¹ 修正两者的固定偏差；偏差超过 2 rad（复活、被规则收走炮权）则走镜头过场而不是瞬移。同一段 3 秒实测：静止帧 **41% → 0.25%**，单帧转角中位数 13.8 → 28 mrad 且第 5 百分位从 0 变成 9.8 mrad，转速变异系数 **1.32 → 0.62**。

**车身振动跟着物理走，不是随机抖，而且刻意做得很轻。** 驾驶舱镜头被螺栓固定在会跑的车体上，所以它带三样东西：随速度变频率与幅度的**履带 / 胎面**双谐波抖动（爬行是低频轻颤，冲刺变高频密振，轮上功率再加一层 38–48 Hz 电机嗡鸣，与胎面波不同相）；纵向速度突变（落台阶、跳跃落地、撞击）触发一次阻尼弹簧**悬挂冲击**，冲击越猛幅度越大；开火时一记俯仰**后坐**（42 mm 约为 17 mm 的两倍）加一点下沉，中弹时一记侧向**肩撞**。弹簧行程限幅 **±1.2 cm / 俯仰 ±0.0075 rad / 侧倾 ±0.003 rad**，并且在瞄准线确定**之后**才加到镜头上——准星始终停在驾驶员放的位置，晃的是它周围的世界。悬挂冲击只在纵向速度突变超过 **0.55 m/s** 时触发（20 Hz 快照的量化噪声、普通悬挂起伏不再被当成落地），弹簧略过阻尼、约 **120 ms** 收敛且不二次回摆；胎面/电机抖动只在车体真正滚动时叠加（原地保持位置也会拉电流，以前这层电流会一直嗡嗡晃镜头），振幅约为上一版的三分之一。**镜头另外还有三层稳定：**眼位高度经过 33 s⁻¹ 的低通（约 30 ms），履带与腿在 20 Hz 采样之间的高频起伏不会一比一翻译成画面上下跳，水平位置保持精确所以视线不会偏离炮线；**亚度级微抖过滤**——指令角与显示角相差小于 0.6° 时以 30 s⁻¹ 收敛，超过就同帧直接跟随，所以按住准星时不再有细微抖动，甩枪也不会有延迟；所有相机缓动改用与帧率无关的指数形式（`1-e^(-k·dt)`），60 Hz、120 Hz 与掉帧时的跟随手感一致，冲击弹簧也按 ≤1/120 s 步长积分，掉帧不会把它激成振铃。实测静止时残余抖动在 0.2 mrad 量级（只剩一点电机嗡鸣），全速行驶时侧倾约 1.5 mrad 峰峰值，压台阶与开火时是一次明确的冲击而不是持续的抖。观战第一视角同样带这套抖动，因为它就是这台车的振动。


驾驶时画面里只保留必要信息：**画面中央**是准星外的一圈枪管热量环与 60° 底盘方位弧，外围三段圆弧依次是超级电容、血量与底盘功率，环右侧是剩余弹量与热量读数；**左下角**是编号/等级、血量、经验、缓冲能量（含功率上限）与超电两张进度条，超电与缓冲只在需要时低头确认；锁定目标时中央下方显示目标与距离。购买结果的弹量与金币来自引擎的 `ammo_purchase` 事件；买不到时引擎会回一条 `ammo_refused`，驾驶端直接显示具体原因（金币不足、本队购买上限已满、需回到补给区或需脱离交战 6 秒）。中弹时画面边缘闪一次红色暗角，和参考客户端的受击反馈一致。

**枪管热量控制按参考模拟器的做法**：每发子弹都要吃热量，热量超过上限引擎会锁枪直到冷却到 0，超过上限 +100（英雄 +200）还会触发永久热锁。驾驶面板会从「弹量与热量的变化」实测出单发热量，按下开火时只要「当前热量 + 一发余量」会越线就不发弹；这个提示**只在按住扳机时**出现（「热量封锁 · 枪口冷却中」），真正过热时才常驻显示「枪管过热 · 冷却中」，所以不会整局挂在屏幕上。余量只留一发，是因为留两发会把可开火区间压到热量条的一半以上，反而不像真车的手感。

**阵亡后镜头锁定。** 被击毁时画面立刻转为灰度，镜头保持在被击毁时的姿态不再跟随鼠标与方向键，屏幕中央叠出**复活面板**：标题「复活中」+ 剩余秒数、免费复活读条（进度与倒计时取自引擎的 `respawn_progress / respawn_required`），以及并排的两个选择——左边是**花费金币立即复活**（`ROUNDUP(已进行分钟数)×80 + 等级×20`，金币不足时按钮变灰并直接写「N 金币不足」），右边是**免费复活**（热键 **Y**，读条结束自动返场）。选「免费复活」会把读条标成已选路径并提示还剩几秒，避免手滑花掉金币。面板底部按客户端惯例给出两行 TIPS，写明两种复活的差别：免费复活保留等级与经验、恢复 10% 血量并进入虚弱，带 30 秒无敌（回己方补给区、基地或完全控制的前哨站增益卡解除虚弱，无敌至少保留到复活后 10 秒）；金币复活血量回满、保留等级与经验，带 3 秒虚弱与无敌、4 秒功率上限翻倍（不超过 200 W）。复活瞬间镜头直接接到新的出生姿态，不会从旧位置旋转过去。被判红牌罚下的机器人不会返场，面板改为「判罚离场 · 红牌」并提示按 P 换一台机器人。红蓝两侧的复活面板用各自队色。

**对局结束即刻收起驾驶界面。** 胜负一判出，左下角那块驾驶/观战状态栏与驾驶舱外壳都随结果卡同时消失，不再压住胜利结算、数据面板与 MVP 卡片的外框；驱动它们的 20 Hz 指令循环也会一起停下，不会继续朝已经结束的对局发指令。观战的第一人称状态栏只在 `frame.status === 'running'` 且不在赛前/结算阶段时渲染，所以回放里翻到终局那一帧同样不会留下残影。

弹药价格按兑换比例执行：17mm 补给区 10 发 / 10 金币、远程 100 发 / 150 金币；42mm 补给区 1 发 / 10 金币、远程 10 发 / 150 金币，并有团队购买上限。本地与远程都可以按任意发数下单、金币按比例扣（例如 17mm 补给区买 7 发扣 7 金币，远程买 50 发扣 75 金币）。两处弹药面板统一为「已有 / 可兑换允许发弹量」读数加一排步进按钮，中心数量默认为 **0**；42mm 的步长为 ±1 / ±2 / ±5 / ±10，17mm 为 ±1 / ±5 / ±10 / ±50。引擎的规则结算每两个比赛节拍跑一次，所以驾驶端把一次下单**排队到下一个结算节拍**再下发，只买一次、不会再出现「按了没反应」。远程订单只有在脱离战斗后才会被引擎接受，送达前弹量不会增加。金币是**本局累计**（击杀、控制区等），开局为 0，所以开局那一波必须回到基地/补给区才能补弹——左下角状态栏会显示当前金币，按下 O / H 时也会先按服务端公布的**兑换比例与团队购买上限**计算能否下单，再判断交战计时；任何一项不满足都会直接说明原因（金币不足、购买上限、补给区/脱离交战条件），不会再出现「条件看起来满足却买不到」。

**弹丸散布。** 两个口径的默认散布半角都收到 **0.3°**（`simulation_assumptions.projectile_spread_half_angle_deg`，17mm 与 42mm 同值）：10 m 内仍落在 125 mm 装甲板轮廓里，15 m 才明显扩散，中距离命中不再靠运气。战场设置仍可按口径覆盖（0–100°），引擎会把覆盖值写进回放校验；`simulation/src/mechanism_tests.rs` 的两个散布测试分别锁住「射线不越出锥角」与「近距近似全中、远距开始掉命中」。

**超级电容与功率**：引擎只接受「功率预算」，不认「一键放电」——`power` 字段（0–200 W）抬高预算后，超过整车功率上限的那部分由超电补足。超电并不是无损的：额定 24 V × 12 A 的输出里只有 **60%** 能送到电机，另外 **40% 在变换与内阻上损耗掉**（`SUPERCAP_LOSS = 0.40`），所以电容放电是「1/0.6 ≈ 1.67 倍」于实际多出来的电机功率，`cap_out = max(0, 电机功率 − 上限) / 0.6`；这部分损耗**不记入底盘功率**，`power_w` 仍只统计真正作用在底盘上的功率（`power_w = 电机功率 − 有用的超电功率 + 回充`），所以功率弧不会因为超电而虚高。按住 C 只有在真正加速、自旋、顶墙时才会把 1800 J 花出去，站着不动只走电池；测试中按住 W + C 加速时，超电每秒掉掉的电量约为「多出上限的功率」的 1.67 倍，松开后按 35 W 的上限回充。

**完全控制的前哨站增益点**和补给区一样能补给自己：站上己方**完全控制**的前哨站增益点（`positions[].controller` 为自己且 `control == "full"`）后，可以按同样的原价买弹，并获得补给区回血速率 **50%** 的治疗（开局 4 分钟后脱战时按脱战档位的 50%）；同时它会解除「虚弱」及其对应的无敌状态，和补给区、基地增益点一致。前哨站被重建后按**实际颜色**判定归属，所以红方前哨站重建为蓝方后，只有蓝方能在那里补给。

**空中机器人不能手动驾驶。** 2027 的空中机器人系统与 2026 的无人机由引擎的自动飞行与撞击逻辑控制，驾驶面板中不会列出它们，接口也会拒绝这类接管请求。

**小陀螺自旋按 `yaw_rate` 通道实现**（与参考模拟器一致的做法）：按住 Shift 时浏览器在下发的动作里加 `yaw_rate`（rad/s）与 `yaw_boost`（0–1 的偏航力矩爆发），引擎的偏航力矩控制器把底盘角速度拉到该目标值，云台继续按世界坐标咬住你的瞄准，所以车体在转、准星不动。目标转速取「引擎 ±12 rad/s 上限」与「该机型云台偏航转速 ×1.7」中较小者，`yaw_boost` 让偏航力矩超过额定值——没有它，额定力矩把自旋卡在 4–5 rad/s，这也是实测「驾驶自旋 ≈ 额定两倍」的来源（重型 3.76→8.98、麦轮步兵 4.55→9.74、轮足步兵 5.00→10.35 rad/s）。策略不下发 `yaw_boost`，所以电脑的自旋完全不变，`simulation/src/spin_tests.rs` 把这两条都锁住了。`yaw_rate` 会覆盖 `heading`，所以自旋时 A / D 变成选方向、不再横移，W / S 依旧驱动底盘，可以边走边转；按住 C 时目标转速直接顶到 12 rad/s。

**底盘正方向跟随云台正方向。** 云台与底盘各有自己的正方向：驾驶时浏览器每 50 ms 把云台的世界朝向作为 `heading` 下发，引擎的偏航控制器把车体转向该方向，云台同时继续咬住世界瞄准点。所以「往前开」永远是往你看的方向开，A / D 平移时车头也不会为了「面向运动方向」而甩动；小陀螺时 `yaw_rate` 覆盖 `heading`，车体才脱离云台自由旋转。

**轮足跳跃用引擎自己的腿推力。** 空格按下后浏览器先发 `leg_height` 把腿压到最短蓄力 0.2 s，再把 `jump` 交给引擎：双腿以 (1 + 推力系数×力度)×重力伸腿 0.16 s，离地后自动收腿；落回地面后再压腿 0.5 s 缓冲。力度取 0.5（额定的一半），抬高约 0.4–0.5 m，仍能越过 0.2 m 台阶；腾空期间浏览器把 `leg_height` 锁在标称腿长，落点姿态更稳。阵亡时跳跃状态机自动归零，不会卡在「腾空」。

**轮足登阶模式（F）。** 所有轮足步兵型号均支持：按住 F 时引擎从**机身外缘**（`radius`，不小于 0.22 m）向外 0.02 / 0.16 / 0.32 m 三处探测台阶高度：只要有一个落差落在 0.04 m 到该机型 `step_climb_m`（+1 cm 容差）之间，就进入一次登阶——腿伸出到最大行程并保持整个登阶过程，随后车体进入 1.3 s 的**搬运伺服**：先把机身抬到踏面之上（上升 0.6 m/s，第一段先升、第二段再前进，避免机身贴着台阶立面时被顶翻），以 1.1 m/s 沿车头方向把轮子送上踏面，再收腿。登阶期间**不触发跳跃推力**、并施加扶正力矩压住俯仰，所以不会再出现「上到一半翻过去」；一次尝试后还会等 0.35 s 让车身在踏面上停稳再判断下一级，避免了以前「上去之后原地抽动」的连环登阶。另外，跨在台阶边缘、两轮都探不到地面时，引擎会把「车身正下方 0.3 m 内最高的地面」当成支撑，驱动不会因为失去抓地力而卡死。轮足步兵的 `step_climb_m` 统一为 0.2 m；其他 `step_climb_m` 为 0 的型号（如折叠麦轮步兵）仍会拒绝 `climb`。实测 RMUC 2027 制高点台阶（第一级立面 0.4 m，之后每级 0.2 m）可以按住 F 连续登上去，机体全程保持直立，单次登阶的离地峰值明显低于一次完整跳跃。

**驾驶时的功率预算。** 平动与小陀螺都按该机型自己的功率预算执行（`power_limit`），不再额外加超电；只有按住 C 时才把预算抬到 200 W，超出上限的部分由超级电容补（并且按 40% 损耗折算放电量），所以超电只在你主动按下时才会掉。电容见底后底盘自然回落到自己的上限，和策略用超电的规则完全一致。

接管只覆盖你驾驶的那一台：同一时刻**策略进程仍在决策**，其余机器人照常按策略行动，比赛记录、回放与 Elo 判定都不受影响。浏览器以 20 Hz 发送操作，服务端在每次物理步进前用这些操作替换该机器人的策略动作。接管是「粘滞」的：短暂网络抖动（0.35 秒无操作）只让机器人刹车，不会交回策略；连续 2.5 秒没有操作（切走标签页、断网）才自动交还，避免策略在你驾驶时插手。被接管的机器人只把炮塔与炮管从画面里去掉，车体照常绘制。

驾驶时比赛速度会被调回 1×，全局快捷键（F 全屏、空格暂停、1–5 切镜头）暂时让给驾驶操作。回放中不能接管。

**局内背景音乐。** 倒计时的「5」一出现就进入局内音乐：先完整播一遍出厂的开场曲 `match-theme.m4a` / `.mp3`，放完接着循环仓库自带的 `summoning-glory.m4a|mp3`；两个文件都解不出来时才直接从老曲开始循环，不会静音。5-4-3-2-1 的报数只是叠在音乐上的蜂鸣。想换成自己的曲子就放 `match-custom.m4a` / `.mp3`，槽位与交接规则见上文「换成自己的音乐」。

**渲染开销。** 第一视角与广播共用一套场景，但会按模式调整开销：阴影刷新按帧时间自适应（见下文），画布像素比上限从 1.6 降到广播 1.3 / 驾驶 1.2，并在此基础上按实测帧时间在 0.6–上限之间自适应调整分辨率；驾驶时还会跳过 R3F 每次鼠标移动都要做的整场景射线拾取。**帧预算按显示器刷新率定**：控制器从渲染回调里测出实际刷新率（平滑后取 10 Hz 整数档），60 Hz 屏仍按 16.7 ms 判定，120 Hz / 144 Hz 屏则按 8.3 ms / 6.9 ms 判定——以前所有屏幕都拿 19 ms 当上限，120 Hz 显示器上只要跑到 ~52 FPS 就被认为「达标」，分辨率不再继续让路，于是永远上不到 120。诊断数据里的 `arenaRender.refreshHz` / `budgetMs` 就是当前使用的这一组值。**阴影降级是唯一的例外，仍按绝对帧时间（>26 ms 才逐级降到每 2/3/4 帧刷新，<18 ms 逐级升回每帧）**：阴影隔 N 帧刷新造成的滞后是 N 个真实帧间隔，若按 120 Hz 的 8.3 ms 预算判定，一帧 13 ms（完全够快）就会被降级，而恢复到每帧又要求低于 9 ms——高刷屏上会让影子明显拖着机体走，所以这条阈值不跟着刷新率缩放。**降档要能证明自己有用**：像素比每降一档，控制器在下一秒核对这个窗口是否真的快了 10 % 以上；如果没有（说明这一帧卡在绘制提交或浏览器合成上，而不是像素数量上），像素比立刻升回去，并在 20 秒冷却期内不再尝试降档——不能把画面糊掉却换不到帧。

驾驶时的两处大头已经改掉：世界坐标里的血条/机构提示是 drei 的 `Html` 覆盖层，每帧都要更新 DOM，驾驶时改为**直接卸载**（不是隐藏），一场比赛里少掉十几个每帧重排的节点；场景树（`ArenaScene`）改为按「战场 + 阵容 + 镜头模式」记忆化，20 Hz 的帧快照不再触发整棵 React 树重建，只让渲染循环从 `feed` 读取位置。React 侧的帧状态也从 20 Hz 降到约 11 Hz（比赛、暂停、状态变化仍然立即渲染）。实测同一台机器上驾驶视角从 ~50 FPS 提升到 ~138 FPS（p50 帧时间 20.8 ms → 6.9 ms）。

**Python ↔ Rust 不是帧率瓶颈（实测）。** 单步往返（Python 组包 → Rust 解算 → 回包 → `json.loads`）在发布版引擎上是 **p50 3.5 ms / p95 4.6 ms / 最大 6.1 ms**，其中 45.7 KB 回包的解码占约 1.3 ms；实时对局循环实测 **19.4–19.8 Hz**（目标 20 Hz）。驾驶指令的 HTTP 往返（keep-alive）**p50 2.3 ms / p95 4.0 ms**（新建连接时的 23 ms 是 TCP 握手，不是服务处理），所以手感延迟主要来自 20 Hz 引擎节拍本身，而不是进程间通信。

**一次策略决策的钱花在哪里（实测拆解）。** 以 2027 内置队伍策略为例，单次决策约 20–25 ms，其中：引擎生成观测约 5 ms（两个观察者一次往返）、**策略自己的计算约 18 ms**（cProfile：`sdk.navigate → _chapter4_navigate → _route` 里的 `clear`/`height` 占 85 %，5 台车各算一次路网可见性）、进程间传输约 3.4 ms。也就是说策略的耗时主要来自它自己的寻路推理，而不是 IPC。

**观测里的静态部分只发一次。** 观测 118 KB 里有 66 KB 是 `arena`（地图、障碍、坡面、路网），整场比赛不变，却被每拍重新 pipe 一遍、在沙盒里重新 `json.loads`。现在引擎的 `observations` 支持 `"static":false`（不带 arena），首次观测把 arena 放进 `__static__` 前缀，沙盒把它缓存起来、每条观测再合并：**单次观测 118 → 59 KB，单次决策的传输成本 3.4 → 1.8 ms（p50），策略拍 p50 从 29.9 ms 降到 20.6 ms**。合并后的观测与引擎完整观测逐键一致（`arena` / `robots` / `robot_models` 相同），同 seed 下**决策与 digest 完全相同**——两条传输路径各跑 40 拍，digest 一致（已作为回归测试固定）。

**多线程已经在了，再加线程帮不上忙。** 同一场的各个策略本来就并行跑：两个队伍策略串行相加 23.3 ms，实际墙钟 12.6 ms（重叠 46 %，剩下的是宿主侧 GIL 与启动抖动）。真正串行的是**单个策略进程内部**——它把 5 台车的寻路放在一个 Python 进程里算，受 GIL 限制；把它拆成多线程只会共享同一份策略状态、并改变决策结果，属于「换打法」而不是「加速」。所以平台的并行放在**策略之间**（自由对战/卡组模式每个策略一个进程，池上限 12/24），单策略内部的成本只能靠策略作者自己优化（例如少算几次 `navigate`、把目标缓存起来）。真要压单策略耗时，可用的杠杆是降低决策频率（`POLICY_INTERVAL`，会改变操作手感）或让慢策略沿用上拍指令（已实现，不阻塞时钟）。

**真正拖慢时钟的是策略阻塞，已修。** 内置 Python 策略下单步 p50 20.9 ms / p95 56 ms；一个 300 ms 的慢 Agent 会把循环压到 **5.5 Hz**（每两拍卡 300 ms）。现在驾驶循环把本拍预算（`DT/speed`）传给 `Battle.step`：决策超时就沿用上一拍的指令、迟到结果直接丢弃（它在下一拍被真正需要时也不再使用），并且**同一策略同时只有一个请求在飞**（工作进程的协议是单请求的，重复提交会让 stdin 错位）。同样的 300 ms Agent 下循环保持 **18.4 Hz**，最长单步 **76 ms**；首次落后会写一条 `policy_lag` 诊断（只记一次，不刷屏、不计入策略错误）。回放校验、无头跑分与单测不传预算，仍是“等满决策”的旧语义，结果不变。

**帧时间优先的三处改动。** 第一，**阴影跟着画面走**：场上一动，阴影贴图就随每个渲染帧刷新，影子始终贴在机体脚下，不再一跳一跳地追着机体（以前按 1–6 Hz 刷新，机体跑起来影子会落后一步）。实测 2027 场地只有约 40 个投影体、33 万个三角形，一次刷新远小于 1 ms；只有实测帧时间超过 26 ms 的机器才逐级改为每 2、3、4 帧刷新一次，恢复到 18 ms 以内再逐级升回每帧；同时把包围球半径小于 16 cm 的零件（螺栓、相机、灯条、装甲边缘）从投影体集合里剔除，它们的影子根本看不见，却各占一次绘制。第二，**着色器预热**改为比赛一开始就用 `renderer.compileAsync` 在并行着色器编译器上编译整棵树（原来是首帧现编，恰好落在开赛那一刻掉一秒帧）。第三，**快照瘦身**：一帧里 `arena / robot_models / rulebook_rules / simulation_assumptions` 这四块是整场比赛不变的静态数据（约占一帧的 55%），现在每条战绩流只在换局时发一次 `static` 消息，之后的快照只带动态部分——实测单条快照从 ~115 KB 降到 ~44 KB，10 Hz 下每秒流量从约 1.9 MB 降到约 0.47 MB。

**鼠标捕获。** 桌面客户端里点画面即进入指针锁定（Pointer Lock），可以无限转动。桌面进程的 Electron 权限处理器显式放行 `pointerLock`，进入驾驶后系统光标会被隐藏并锁定，鼠标只提供相对位移，不会跑到窗口边缘或离开战场；画面中心固定的准星就是此时的鼠标位置。部分宿主（VS Code 内置浏览器、iframe 预览）**直接禁止指针锁定**，这时会提示「此环境不允许锁定鼠标」，并把光标整页隐藏：视角仍然跟随鼠标位移转动，只是指针移出窗口后会停止。需要完整的锁定手感请用桌面版（`python scripts/project.py desktop`）。

## 回放与录像：用途不同

| 方式 | 保存什么 | 之后可以做什么 |
| --- | --- | --- |
| 数据回放 | 帧、事件与比赛元数据 | 暂停、拖动时间线、换镜头、查看状态 |
| 视频录像 | 当时选定镜头和界面的画面与音轨 | 在播放器中观看和分享 |
| 数值重演校验 | 用记录的动作重新运行匹配引擎 | 检查重演结果，需要相同规则与仿真构建 |

在“比赛与回放”中选择记录可加载、导出或删除，也可以导入本地回放文件。删除数据前请保留想长期保存的导出副本。当前 v4 回放复用静态场景数据，桌面包保留历史素材与 v2 引擎用于兼容。

源码环境中可执行：

```sh
uv run python -m rmuc_arena verify-replay path/to/match.json
```

**能够播放旧回放，不等于能用当前引擎通过数值重演。** 2026 回放也不会因为你当前选择 2027 而更换比赛规则。

## 流畅度：每帧的钱花在哪里 {#performance}

广播画面是 three.js 实时渲染 + 9 Hz 的 React 快照刷新，所以"卡"通常来自两处之一：**每帧的绘制次数**，或**快照之间的插值**。两者都可以在浏览器控制台里直接量：

```js
arenaRender        // {calls, triangles, meshes, shadowCasters, materials, dpr, shadowEvery, eye}
arenaCensus()      // 按最近命名祖先 / 网格名统计：谁占了几百次 draw call
arenaScene         // 场景根节点，配合 scene.traverse 做临时实验
arenaDiagnostics() // 含 pace（实测快照间隔）、prematch、audio、reel 等
```

已做的两件事：

- **阴影投射体按半径裁剪。** 以前每个网格都强制投影，一个底座就有 100 多个投射体，每次阴影刷新都是全额重画。现在只有 BoundingSphere 半径够大的部件投影（机器人 0.16 m、场景 0.45 m 起），实测投射体 **96 → 33**。
- **按关节烘焙颜色与表面参数。** 机型资产几乎每个零件一个材质，按材质合并几乎没有效果。改为把每个零件的**颜色、粗糙度、金属度**烘进顶点属性（`aSurface`，由 `rigidMeshes.ts` 里的着色器注入读取），再在**每个可动关节内**合并：车体、云台、枪管、每个轮子、每条腿节各剩一两次 draw call，而引擎驱动的关节节点本身不动。实测机器人网格 **120 → 37、87 → 23~26**，整场 **calls 1055 → 736、meshes 1242 → 891**，p95 帧时间 **13.9 ms → 7.1 ms**。新增可动节点必须写进 `ROBOT_JOINT`（`rigidMeshes.ts`），否则它的零件会被烘进上一个关节。

**插值跟着实测节奏走，并且再也不外推。** 引擎名义上是 20 Hz，但一次策略决策可能占住 200 ms，实际快照间隔常在 20–100 ms。过去按写死的 50 ms 插值，每个周期最后一段机器人是**完全静止**的（看起来就是一顿一顿）。现在客户端平滑统计真实到达间隔（`arenaDiagnostics().pace`），按它插值：实测冻结帧 **12 % → 7 %**。

这一轮又补了两处，都是同一件事的两半：

- **不再外推（`feedPhase`）。** 旧代码允许相位冲过 1.0（最多 1.3 倍），也就是用上一个步长去猜下一段运动。速率一旦变化——驾驶员刚开始或刚停手就是这种情况——猜出来的点必须被拽回真实值，那一下回跳就是画面里的抽搐。现在相位最多只到 **1.18 倍**，而且只有 Hermite 曲线才允许越过 1.0：它是三次曲线，位置和速度都连续，越过最新样本的那一小段沿同一个速度继续，回包落地时接着走，不会回跳。
- **速度连续（`robotWorld`）。** 两帧快照之间原本是直线插值：位置连续，**速度不连续**，每个快照交界处都用同一个速度突变，即使 140 fps 也能看出「一格一格」。引擎本来就发布每个刚体的 `vx / vy / vz`，于是改用**三次 Hermite**（两端切线取两个样本自己的速度），快照交界处不再有速度台阶；复活瞬移、位置跳变超过 2 m 等异常情况自动退回直线插值，不会出现绕空的弧线。

这两条合起来就是「补帧」：实测第一人称一段 2.6 s 的转向里，`arenaMotion.alpha` 有 **14–22 %** 的帧越过 1.0（旧的实现到 1.0 就冻住），也就是那些原本会静止的帧现在还在动。

**驾驶视角本来就不慢，慢的是镜头。** 第一人称实测（1600 × 1000、dpr 1.05、阴影每帧刷新）：**GPU 3.5–4.2 ms、绘制提交 2.7–4.6 ms、可见 draw call 49–149**——因为镜头在场地内部，场馆与远端机体被视锥剔掉了。所以「一卡一卡」不是帧率不够，而是上面那条镜头角度的采样问题；这一轮把「跟手」修好之后，同一段实测的最慢帧也从 15.7° 的单帧转角降到 11.6°（且那是 dt 29 ms 的慢帧本身带来的，不是跳变）。

还剩的优化路径（按收益排序）。先看实测数据：2027 场地、1600 × 1000 的广播画布上，用 `EXT_disjoint_timer_query_webgl2` 量到的**整帧 GPU 时间只有 4–5 ms**，绘制提交（`gl.render` 的 CPU 时间）约 5.4 ms / 712 次 draw call，两者基本相等，说明这一帧是**卡在绘制提交上**，而不是像素量上：

- **把分辨率降到 0.6 倍，GPU 时间从 4.44 ms 变成 4.52 ms——完全没动。** 像素数不是瓶颈，所以"卡就降分辨率"是错的（自适应控制器会先验证降档是不是真的更快，不更快就把清晰度还回来）。
- **关掉阴影只省 0.3 ms**（4.44 → 4.16）：4096² 阴影图看着吓人，深度pass 的着色成本其实很低。
- **藏掉 8 架无人机（96 次 draw call）也在噪声里**：单次 draw call 的成本远低于"总调用数 × 常数"的直觉。
- 主线程 65 % 的时间在空转，我们的 JS 约占 5 %；一帧约 845 个可见网格对应 348 个独立材质（机型资产几乎每个零件一个材质，逐帧还被驾驶座舱改自发光）。
- **服务端不是帧率的瓶颈**：2027 5v5（120 Hz 物理）跑起来时，服务端进程树约占 **0.6 个核**，其中 Rust 引擎子进程 **49.8 %**、python 主进程（WebSocket + 帧序列化）**11.1 %**、策略进程约 0 %。**调低策略决策频率省不下渲染时间**，它只影响比赛时钟与响应；真要压服务端开销，动的是引擎 tick 而不是决策频率。而它和浏览器是不同进程，浏览器该掉帧还是掉帧。

1. **底座 / 前哨站 / 基地的阵营发光件**：这些零件用 `Team*` 材质，驾驶座舱会逐帧改它们的自发光，所以现在不能合并（两个底座仍各占 61 次 draw call）。把它们也做成顶点属性 + 实例化着色器是收益最大的一步。
2. **同型机体**：8 架无人机现在各 12 个网格（机壳按材质合并、每个旋翼的桨毂与桨叶已经并成一次绘制），同型机体之间再用 InstancedMesh 可以把这个数字再压一截；同型号机器人同理，但它们各自有独立的关节姿态，收益远小于无人机。
3. **装甲编号**：每台机器人 4 片编号牌、每片 2 个三角形，却各占一次绘制（10 台共 80 次），改成每台一次 InstancedMesh 就能降到 20 次。
4. **场地贴花与区域圆环**：地图里 36 个透明 `MeshBasicMaterial` 贴花、以及 `Zone` 每区 2–4 个逐帧改色的网格，改成顶点色 / 实例色可以一次画完（贴花不能按材质合并，因为它们各自带烘焙好的接触阴影 `aoMap`）。
5. **炮镜双渲染**：开镜时整场景要渲染两遍（先渲进贴图再放大），这是第一人称最贵的一帧。

这一轮已经落地的是：能量单元这类道具模型不再按零件逐个绘制（`batchStaticStructure` 支持只做颜色合批、保留阴影）；**导出器把"混合"留在实心材质上**的零件现在也能进批次了——全不透明、普通混合、写深度的面片画出来的像素和绘制顺序无关，所以它们不再被排除在合批之外（真会混合的玻璃、发光面、贴花照旧单独排序）；无人机的每个旋翼也按"旋翼子树"合并，桨毂和桨叶从两次绘制变一次（8 架共省 32 次 draw call）；以及上面那条**分辨率降档必须先证明有用**的规则——它让"明明不是像素不够、却把画面降到 0.6 倍"的情况不再发生。

## 一个有效的复盘顺序

1. 先确认这局的赛季、对手、阵容和种子，避免拿不同条件直接比较。
2. 2027 先看哪一段控制度开始拉开，再回到当时的控制点。
3. 检查丢点的机器人是否缺弹、过热、阵亡、视野受阻或路线受限。
4. 只改一个明确问题，重新练习并提交新版本，再与相同条件下的旧版本比较。
