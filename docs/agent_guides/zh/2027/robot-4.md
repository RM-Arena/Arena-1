# 机器人策略对战 · 单机器人赛参赛手册（RMUC 2027 · 4 号步兵）

本手册是 **RMUC 2027 规则**下单机器人赛的完整规则与接口说明。你要编写一个 Python 程序，**只控制己方 4 号步兵**。己方另外四台机器人分别由其他参赛者独立编写的程序控制：你们共享金币与胜负，可以通过队内消息通信。比赛过程中不会调用语言模型，所有决策都由代码实时做出。

## 速览

| 项目 | 内容 |
| --- | --- |
| 交付物 | `strategy.py`，其中定义 `act(observation, state)` |
| 你控制 | 己方 4 号步兵（`controlled_ids == ["4"]`） |
| 队友 | 己方其余四台，由其他参赛者的程序控制，支持队内通信 |
| 决策节奏 | 每 0.1 s 调用一次 `act`，每次须在 200 ms 内返回 |
| 单局时长 | 420 s；任一方基地被击毁时提前结束 |
| 开发时间 | 默认 90 分钟，由组织者启动计时；阅读、编码、测试、提交全部计入 |
| 参赛版本 | 截止前最后一次成功提交的版本 |

**上手步骤**

1. 运行 `python3 -B arena.py status`，确认开发计时已经开始，记下剩余时间。
2. 阅读本手册。第一遍可以只读「任务与限制」「比赛概览」「控制点与控制度」「兵种机制」「接口参考」，其余章节需要时再查。
3. 阅读 `strategy.py`。它是一个可以直接运行的模板，已经实现补弹、重型装配与安装发射模块、哨兵姿态、空中机器人撞击前哨与基地、步兵推进与占点等基本行为。
4. 跑一局短练习，确认环境正常：`python3 -B arena.py test --duration 30`。
5. **尽早提交一次**：`python3 -B arena.py submit`。这样无论之后发生什么，你手里都有一个有效版本。
6. 之后反复迭代：修改 → 练习 → 查看结果与回放 → 提交。

## 1. 任务与限制

### 1.1 交付物

你只需要交付 `strategy.py`。它必须定义函数 `act(observation, state)`，并返回 `(actions, new_state)`。调用方式与数据格式见「接口参考」。

### 1.2 开发时间

- 默认总开发时间为 **90 分钟**，由组织者启动计时。阅读、规划、编码、练习、等待结果和提交都计入同一个连续的时间窗口。
- `python3 -B arena.py status` 显示主机记录的剩余时间。计时尚未开始时，工具会提示等待组织者启动，此时不能练习或提交。
- 截止前可以任意修改、练习和多次提交。**截止前最后一次成功提交的版本就是参赛版本**；一次都没有成功提交则没有参赛版本。
- 截止后不再接受新的练习和提交，正在进行的练习会被停止。截止后对文件的修改不会影响已提交的版本。
- 开发阶段的 90 分钟与比赛内的 420 s 是两个独立的时钟。

### 1.3 文件与权限

**只修改 `strategy.py`。** 工作目录中的其他文件都是受保护的参考资料或工具；修改、删除它们或新增文件，都会导致练习和提交被拒绝。唯一的例外是 `practice/` 目录：你可以在其中保存练习脚本、笔记、日志和回放，但这些文件不会进入比赛环境，`strategy.py` 不能依赖它们。

| 文件 | 用途 |
| --- | --- |
| `strategy.py` | 你的策略代码，唯一可编辑的文件 |
| `AGENT_GUIDE.md`、`AGENT_GUIDE.en.md` | 本手册的中文版与英文版，内容一致 |
| `AGENT_TASK.md` | 任务摘要 |
| `sdk.py` | 比赛环境中可以 `import` 的辅助库 |
| `arena.json` | 地图、规则参数与机器人设计的完整数值 |
| `agent.json` | 你的参赛信息与练习凭证 |
| `arena.py` | 练习与提交工具 |
| `practice/` | 可自由写入的练习产物目录 |

不要查看或尝试获取其他参赛者的代码、私有状态、提交或日志。

### 1.4 运行环境与限制

比赛时，你的程序在独立容器中运行，容器里只有你的 `strategy.py`：

- Python 3.12，只能使用标准库和 `sdk.py`；
- 无网络，根目录只读，非 root 用户；单进程，不能创建线程或子进程；
- 内存 1 GiB，CPU 1 核；
- 源码不超过 512 KiB；
- 每次决策限时 **200 ms**；启动时的模块导入与全局初始化不计入单次决策时限，但须在 60 s 内完成；
- 返回的动作总计不超过 16 KiB，每台机器人的动作不超过 1 KiB；
- `new_state` 必须能序列化为 JSON，且不超过 256 KiB。

单次决策超时只跳过本轮动作，程序和私有状态会保留；迟到的动作会被丢弃，下一轮使用最新观测继续决策。每轮仍只有 200 ms 的真实时间预算，等待上一轮返回也计入该预算；成功返回一轮新动作后，连续超时计数清零。任何策略异常（包括恢复成功的超时）都会保存在回放中，该局不计入 Elo。

出现以下任何情况，你的程序会在**本局剩余时间内被停用**——比赛照常进行，但这个进程控制的机器人此后不再收到任何指令：

- 连续 3 轮决策超时，或 `act` 抛出异常；
- 返回值格式错误，或动作中含有不支持的字段、非有限数值（NaN、Infinity）；
- 试图控制不属于你的机器人；
- 超出上述大小限制。

所以请在 `act` 内部做好异常保护，并在练习中检查最坏情况下的耗时。练习对局使用与正式比赛相同的容器和限制。`print` 的输出会进入错误日志，只在程序出错时随练习结果返回。

### 2.4 胜负判定

- **只有一种情况会提前结束比赛：任一方基地被击毁**（剩余基地血量高的一方获胜）。地面机器人全部阵亡不会结束比赛，阵亡的机器人可以复活。
- 420 s 时间到，依次比较下列各项，先分出高下的一方获胜：
  1. **控制度**（见「控制点与控制度」）；
  2. 全队攻击伤害（对机器人、前哨站和基地造成的有效伤害之和）；
  3. 存活地面机器人的剩余血量之和；
  4. 仍然相同则为平局。
- 注意：与 2026 不同，到时比较的第一项不是基地血量，而是控制度。

## 4. 信息与控制

### 4.1 你控制什么

你的程序只控制己方 4 号。`observation["controlled_ids"]` 恒为 `["4"]`，返回的 `actions` 只能包含键 `"4"`；出现其他编号会导致程序被停用。己方另外四台由其他参赛者的独立程序控制，你们共享金币、基地、控制点与团队增益，可通过 `messages` 通信，但看不到彼此的代码、私有状态，视野也不自动共享。

### 4.2 你能看到什么

**视觉观察（受视野限制）**

- `observation["enemies"]` 只包含当前至少被一台由本进程控制的己方观察者看到的敌方机器人（包括残骸），带外观可见的全部状态。
- 观察者是己方存活的地面机器人。视距：重型 18 m，步兵 18 m，哨兵 20 m。**机库没有相机，空中机器人也不回传画面**，因此 6 号不提供视野。观察者从相机位置向目标车体中心、云台顶部和四块装甲板分别看去，任一视线不被墙体、地形、结构或其他机器人挡住、且位于相机视锥内就算看到。
- 地面相机的水平视场为100°、垂直为70°，随实际炮口方向转动。
- `observation["enemy_drones"]` 是观察者看到的敌方空中机器人（位置、速度、状态）。
- 敌方弹丸只在视野内可见；己方弹丸始终可见。能量机关目标只在己方观察者与机关中心的距离不超过视距时提供。

**公开信息（不受视野限制）**

- 双方全部机器人的编号、兵种、血量、血量上限和存活状态（裁判快照 `referee`，不含位置）；
- 双方基地与前哨站的血量、归属、装甲状态与是否曾被击毁；
- 四个控制点的控制方与进度（`positions`），双方控制度（`referee["control"]`）；
- 双方攻击伤害累计、双方科技核心装配状态、各增益卡的占领状态；
- 己方全部机器人的完整状态（含空中机器人）和己方经济（含物流系数 `referee["logistics"]`）；
- 地图、规则参数和机器人设计。

**不公开**：对方的金币、弹量、热量、经验、代码和私有状态；看不到的敌方机器人的一切位置信息。瞄准只能使用 `enemies`或队友主动发来的情报。

## 5. 规则

### 5.1 伤害与射击

| 来源 | 伤害 | 有效条件 |
| --- | --- | --- |
| 17mm 弹丸 | 20 | 命中装甲板，法向速度 > 12 m/s；同一块装甲 0.05 s 内只结算一次 |
| 42mm 弹丸 | 200 | 法向速度 > 8 m/s；同一块装甲 0.2 s 内只结算一次 |
| 空中机器人撞击 | 200 | 只对基地装甲与前哨站中层装甲有效；见「空中机器人系统」 |

- 实际伤害 = 基础伤害 × 攻击倍率 ×（1 − 防御 + 易伤），四舍五入。同类增益取最大值，不叠加。
- **42mm 弹丸只在本队重型机器人“在线”时有效**：重型最近 4 s 内射击过，且存活（或阵亡不足 3 s）。重型的第一发 42mm 用于完成安装，不造成伤害、不计热量与超速。
- 热量：17mm 每发 +10，42mm 每发 +100；按冷却速率每 0.1 s 结算。超过上限即锁定发射，直到热量降到 0；超过上限 100（17mm）/ 200（42mm）以上会**永久锁定**。
- 超速：17mm 上限 25 m/s，超出 0–5 / 5–10 m/s 分别锁定 15 / 20 s，超出 10 m/s 以上永久锁定；42mm 上限 16.5 m/s，18 m/s 以内锁定 15 s，以上永久锁定。所有默认型号的出膛速度都低于上限。
- 机器人阵亡后残骸留在场上，会挡路、挡视线；阵亡瞬间热量清零。

### 5.2 金币、弹药、回血与复活

- 1 s 时双方各得 800 金币；61、121、181、241、301 s 各 +100；361 s +300。科技核心装配另有收入（见「科技核心装配」）。
- 兑换弹量（`buy_ammo={"amount": n, "remote": bool}`）：

| 弹种 | 就地兑换 | 远程兑换 | 全队上限 |
| --- | --- | --- | --- |
| 17mm（步兵、哨兵） | 10 发 / 10 金币，须为 10 的倍数 | 100 发 / 150 金币，6 s 后到账 | 1000 |
| 42mm（重型） | 1 发 / 10 金币 | 10 发 / 150 金币，6 s 后到账 | 100 |

  就地兑换需要在**己方基地、己方补给区、己方制高点**，或**被本队完全控制的前哨站**增益卡上（离开后 2 s 内仍算）；远程兑换需要“脱战”（最近 6 s 内没有射击也没有受伤）。虚弱状态不能兑换。
- 远程回血 `remote_heal=True`：脱战时花费 50 + ⌈t/60 × 20⌉ 金币，6 s 后回复 60% × λ 的血量上限。
- 补给区回血：每秒回复血量上限的 10% × λ；240 s 后脱战时为 25% × λ。在被本队完全控制的前哨站增益卡上回血速度减半。
- **物流系数 λ = 1 − 基地已损失血量 / 20000**（`referee["logistics"]`）。基地掉血越多，回血越慢、复活越慢。
- 复活：阵亡后复活进度每秒 +1（在己方补给区，或己方基地血量低于 4000 时每秒 +4）；需要的进度为 (10 + t/10 + 20 × 已立即复活次数) / λ。普通复活回复 10% 血量、30 s 无敌，处于“虚弱”状态（不能射击、不能获得增益）直到回到己方基地或补给区（或完全控制的前哨增益卡）。
- 立即复活 `revive=True`：花费 ⌈t/60⌉ × 80 + 等级 × 20 金币（哨兵按 1 级），满血复活，虚弱和无敌均在 3 s 后解除，4 s 双倍功率。
- 金币为全队共享。同一时刻多台机器人消费时按编号顺序结算，余额不足的请求直接失败。

### 5.3 控制点与控制度

2027 规则的核心是四个**控制点**（`observation["positions"]`）：

| 控制点 | 组成 | 说明 |
| --- | --- | --- |
| `red_outpost` / `blue_outpost` | 该方前哨站增益卡 + 该方中央高地增益卡 | 开局由所属方完全控制 |
| `red_base` / `blue_base` | 该方基地增益卡 + 该方堡垒增益卡 | 只有原所属方能完全控制 |

- 每个控制点有 `controller`（控制方）与 `control`（`full` 完全 / `temporary` 临时）。
- **夺取**：在对方完全控制的控制点上，只有你方机器人激活其任一增益卡、对方没有机器人在卡上，持续 5 s 后变为你方**临时控制**。中途离开时进度以同样速度回退；双方同时在卡上时进度暂停。
- **转为完全控制**：临时控制方连续 5 s 没有机器人在卡上，控制点转为另一方的完全控制（前哨控制点）；基地控制点则总是回到原所属方。
- **前哨站被击毁**：完全控制 → 同一方临时控制；临时控制 → 同一方完全控制。当前哨控制点因此或因上一条转为某方的完全控制、而前哨站已毁时，前哨站**为新控制方以 500 血量重建**，它此后是该方的前哨站（自己的弹丸不再伤害它）。
- **控制度**：同时控制（完全或临时）双方的前哨控制点时每秒 +1；同时控制双方的基地控制点时每秒 +3。控制度只增不减，是到时判胜的第一依据。
- **基地无敌**：一方完全控制自己的前哨控制点时，该方基地不受任何伤害。想打基地，必须先夺取（或通过击毁前哨让对方失去）对方前哨控制点的完全控制。
- 中央高地增益卡互斥：已占据的一方优先，另一方的机器人无法激活。

### 5.4 建筑与堡垒

- 基地 10000 血；前哨站 1000 血（重建后 500）。前哨站三块中层装甲随转子旋转，180 s 后停止；顶层装甲在 2027 中不计伤害。
- 基地的三块上层装甲始终可以被 17mm、42mm 和空中机器人撞击击中；三块大装甲在“开启”后才暴露。**基地装甲由敌方在你方堡垒上累计停留 10 s 打开**（离开超过 3 s 计时清零）。
- **己方堡垒**：己方失去对己方前哨控制点的控制时（被对方临时或完全控制）启用。一台己方机器人占卡：防御 50%，冷却加成 min(75, ⌊基地最大掉血/80⌋)，并解锁一份储备弹量 min(500, 100 + ⌊基地最大掉血/15⌋)：在卡上射击时先用储备（重型每发 42mm 消耗 10 份）。
- **敌方堡垒**：180 s 后，控制着对方前哨控制点的一方可以激活对方堡垒卡（承受 100% 易伤），持续 10 s 打开对方基地装甲，并为本方提供基地控制点的临时控制进度。

### 5.5 增益卡与地形跨越

| 增益 | 条件 | 效果 |
| --- | --- | --- |
| 基地 | 己方基地卡 | 防御 50% |
| 制高点 | 己方制高点卡 | 防御 50%，可就地兑换 |
| 中央高地 | 中央高地卡（互斥） | 防御 25% |
| 补给区 | 己方补给区 | 回血、加速复活、就地兑换；重型在补给区内无敌 |
| 装配 | 己方装配区，装配进行中 | 重型累计 45 s 无敌（每次刷新最高装配等级时重置） |
| 公路跨越 | 3 s 内从公路低端卡到高端卡 | 防御 25%，5 s，冷却 15 s |
| 高地跨越 | 5 s 内从高地下卡到中央高地卡 | 防御 25%，30 s |
| 隧道越过 | 3 s 内经过隧道两端卡（从顶上） | 防御 25%，30 s |
| 隧道穿越 | 3 s 内两端卡之间经过隧道中段卡（钻过去） | 冷却 ×1.5，120 s |

- 步兵首次完成公路、高地、隧道跨越以及首次登上制高点，各获得 300 经验。

### 5.6 科技核心装配

装配由**重型机器人**完成（2027 没有工程机器人）：重型在己方资源岛拾取能量单元（每队共 6 枚，最多同时携带 2 枚），开到己方装配区，用机械臂把能量单元装入科技核心。

- 可开始时间：1 级 0 s、2 级 60 s、3 级 120 s、4 级 180 s，且必须先完成前一级。
- 步骤（每 0.1 s 结算一次动作）：1 级 插入 → 确认；2 级 插入 → 抬升 → 确认；3、4 级 插入 → 抬升 → 翻转 90° → 旋转到目标角度（±5°）→ 确认。每步都校验真实机械臂末端、工具方向与腕角；3、4 级旋转到位保持 0.4 s 后可确认，错误确认有 1 s 重试锁定。
- 4 级需要**两个**核心（自己的和“借用”对方的），每队只能完成一次，限时 45 s；插入、抬升、旋转到位与确认均须在 5 s 内在两个核心上成对完成（翻转步骤除外）。双臂型号可以用 `assembly_core=2` 同时操作两个核心；单臂型号用 `assembly_core=0/1` 交替。
- 首次完成奖励：

| 等级 | 奖励 | 之后重复完成 |
| --- | --- | --- |
| 1 | 重型升到 5 级；科技收入 +40 / 10 s | 每 10 s +4 |
| 2 | 重型 7 级；步兵等级上限 7；收入 +20 | 每 10 s +8 |
| 3 | 重型 10 级；步兵等级上限 10；全队防御 25%；**解锁重型发射机构**；收入 +20 | 每 10 s +12 |
| 4 | 全队防御 50%；收入 +40 | 不可重复 |

- 1–3 级没有额外尝试时限，完成后可立即开始下一次；4 级从核心到位起计时 45 s。失败后同难度的位姿和目标角度保持，成功后才抽取下一组。装配进行中重型不能射击；阵亡或连续 15 s 未检测到装配卡则本次失败。

### 5.7 能量机关

- 能量机关位于场地正中 (14, 7.5) 的龙门上，红蓝两面共轴同步转动，各有 5 个灯臂（目标半径 0.15 m，旋转半径 0.7 m）。双方各自激活，只能击打朝向自己的一面（转轴方向见 `arena["rune"]["axis_yaw"]`）。
- **步兵或哨兵**发起激活：`rune_start=True`（存活、不虚弱即可，不限位置）。只能用 17mm 击打，法向速度须超过 12 m/s；42mm 无效。
- 目标在 `observation["runes"][己方]["targets"]`（`arm, x, y, z, radius, lit`），`lit=True` 是现在应该击打的目标；只有己方观察者在视距内时才提供位置。瞄准时用 `dict(target, kind="rune_target")` 传给 `sdk.aim_pitch`。
- 小能量机关（0–180 s，0 s 与 90 s 各 1 次机会）：依次在 2.5 s 内击中 5 个不同的灯臂即激活；打错或超时进度清零，整个过程限时 20 s。效果：全队与建筑防御 25%，持续 45 s，期间步兵经验翻倍（全队额外最多 1200）。
- 大能量机关（180、255、330 s 各 1 次机会）：每轮亮 2 个目标，第一个须在 2.5 s 内击中，之后 1 s 内可再击中第二个；共 5 轮，有效命中 5–10 个。按平均环数获得攻击倍率 1.5–3、防御 25–50%、冷却 ×1–×5，持续 30–60 s；存活步兵平分 750 经验。
- 运动规律：小能量及未处于激活流程的大能量以 π/3 rad/s 匀速转动；正在激活的大能量使用 a·sin(ωt)+2.090−a，每次开始大能量激活重置 t、a、ω，红蓝两面共用同一转轴。
- **2027 收缩规则**：本队第 1 次激活大能量机关后，之后的激活只有 4 环及以上（更靠近中心）的命中有效；第 2 次之后只有 7 环及以上有效（环数：离中心每 1.5 cm 少 1 环，正中 10 环）。

## 7. 接口参考

### 7.1 act 函数

```python
def act(observation: dict, state) -> tuple[dict, object]:
    ...
    return actions, new_state
```

- 每 0.1 s 调用一次。比赛状态每 0.05 s 推进一步，所以 `tick` 每次决策增加 2；第一次调用时 `tick == 0`。
- `actions` 以编号字符串为键、动作字典为值，例如 `{"4": action(...)}`。没有给出动作的机器人本轮视为空动作（停下、不射击）。
- 动作在下一次决策前持续生效（0.1 s，即 2 个比赛步）。
- `state` 是你上一次返回的 `new_state`，第一次调用时为 `None`。它必须能序列化为 JSON，且不超过 32 KiB。
- `random` 模块已用固定种子初始化。不要依赖系统时间，请使用 `observation["time"]`。

| `yaw_rate` | rad/s，±12 | 地面 | 底盘目标角速度（小陀螺），优先于 `heading` |
| `aim`、`pitch` | 弧度 | 地面 | 云台世界水平角、俯仰角 |
| `fire` | bool | 地面射手 | 本次决策期间是否射击 |
| `power` | 瓦 | 地面 | 底盘功率预算 |
| `buy_ammo` | `{"amount": n, "remote": bool}` | 重型、步兵、哨兵 | 兑换弹量 |
| `remote_heal` | bool | 地面 | 远程回血 |
| `revive` | bool | 地面 | 阵亡时立即复活 |
| `transform` | bool | 折叠型号 | 折叠 / 展开炮塔 |
| `profile` | 字符串或字典 | 步兵 | 性能选择，仅 `tick == 0` 有效 |
| `rune_start` | bool | 步兵、哨兵 | 发起能量机关激活 |
| `messages` | 列表 | 全部 | 队内消息，见「队内通信」 |

不适用于当前机器人或当前状态的操作不会生效，有的会以 `invalid_action` 事件记录在回放中。字段名拼错会让整个程序被停用；`sdk.action` 会在你的代码里提前报错。

### 7.4 SDK

`sdk.py` 是比赛环境中唯一可以导入的辅助库。它只做公开计算，不会给出额外信息。2026 的通用函数（`nearest_enemy`、`aim_at`、`aim_pitch`、`ballistic_reachable`、`intercept`、`can_fire`、`navigate`、`toward`、`distance`、`terrain_height`、`referee_info`、`message`）在 2027 同样可用，并已按赛季处理 42mm 弹道、重型发射机构状态与禁区。2027 新增：

| 函数或常量 | 作用 |
| --- | --- |
| `rules(obs)`、`RULES_2027`、`season_of(obs)` | 当前赛季的完整规则参数 |
| `TEAM_SLOTS_2027`、`DESIGNS` | 2027 编号与机器人设计 |
| `position(obs, name)`、`controls(obs, name, team=None)`、`control_degree(obs, team=None)` | 控制点与控制度 |
| `zone_center(arena, zone_id)` | 增益卡中心，例如 `"blue_central"`、`"red_supply"` |
| `workbench_point(robot, arena)`、`launcher_ready(robot)` | 工作台停靠点；发射机构是否已解锁待安装（未解锁时也可提前安装，见「重型机器人」） |
| `resource_pickup_point(robot, arena)`、`assembly_work_point(robot, arena)` | 资源岛拾取点、装配停车点 |
| `drones(robot)`、`strike_plan(drone, plate)`、`hostile_plates(obs, kind)` | 空中机器人列表、撞击规划、可撞击的装甲 |

瞄准前哨站时传入 `dict(obs["outposts"][对方], kind="outpost")`，瞄准能量机关目标时传入 `dict(target, kind="rune_target")`。`sdk` 在导入时预先计算两个赛季的导航图，这部分时间不计入决策时限。

### 7.5 队内通信

所有控制模式都支持按机器人编号通信。每台机器人可在自己的动作中设置 `messages`，每轮最多发送4条；消息在下一次决策（0.1 s后）送达，不受距离、视野或机器人存活状态限制。

单机器人进程继续通过 `obs["messages"]` 接收发给自己的消息；`obs["message_inboxes"][obs["controlled_ids"][0]]` 提供同一收件箱。

```python
from sdk import action, message

def act(obs, state):
    slot = obs["controlled_ids"][0]
    received = obs["messages"]
    return {slot: action(messages=[message({"intent": "advance"})])}, {"received": received}
```

- `message(data)` 广播给当前己方其余机器人；`message(data, to="2")` 发给指定己方部署编号。在固定阵容中编号为1、3、4、6、7，自由赛以实际阵容为准。不能发给自己或对方，发送者由宿主机从动作编号确定，不能伪造。
- 原始格式为 `{"to": "all" 或队友编号字符串, "data": JSON值}`。每条 `data` 最多512 bytes，消息与物理动作一起计入每台机器人1 KiB动作上限；这个额度按机器人计算，全队进程不会共享一个4条的限额。
- 收件信封为 `{"from": "red-1", "to": "red-2", "tick": 0, "delivery_tick": 2, "data": ...}`。首轮收件箱为空，下一轮只出现一次；需要保留的情报自行存入 `state`。
- 同轮消息按发送者部署编号、消息列表顺序送达，与策略动作字典顺序或进程完成顺序无关。不存在的自由赛接收者不送达；程序停用后不再发送或处理消息。
- 消息不会改变视觉 `enemies`，也不会给独立进程自动共享私有状态。主动报告看到的敌人、目标和计划时，应附带时间并处理情报时效。
- 回放的决策步 `actions[i]["communication"]` 保存发送者、接收者列表、发送与送达tick及内容；消息不交给物理引擎，也不在第二个保持动作的比赛步重复发送。

## 8. 练习与提交

所有命令都在你的工作目录中运行：

```bash
python3 -B arena.py status                  # 剩余时间、已提交版本、练习任务
python3 -B arena.py test [选项]              # 用当前 strategy.py 启动一批练习对局
python3 -B arena.py results JOB_ID           # 查看练习进度与结果
python3 -B arena.py replay JOB_ID --game 0   # 把第 0 局的完整回放保存到 practice/
python3 -B arena.py submit                   # 提交当前 strategy.py
```

### 8.1 练习对局

| 选项 | 默认 | 说明 |
| --- | --- | --- |
| `--opponent` | `baseline` | `baseline`：公开基准策略（偏防守）；`self`：和当前代码自己对战；也可以填 `status` 中列出的你自己已提交的版本号 |
| `--duration` | 30 | 每局时长（秒），1–420；正式比赛为 420 |
| `--games` | 1 | 局数，种子从 `--seed` 起依次加 1 |
| `--seed` | 42 | 第一局的种子 |
| `--swap-sides` | 关闭 | 每个种子红蓝各打一局，局数翻倍 |

```bash
python3 -B arena.py test --opponent baseline --duration 30
python3 -B arena.py test --opponent self --duration 420 --games 4 --swap-sides
python3 -B arena.py test --opponent 版本号 --duration 420 --games 2 --seed 200
```

- 启动时会给当前 `strategy.py` 拍快照，之后修改文件不影响这批对局。
- 同一时间只能运行一批练习，服务繁忙时会排队。排队和运行时间都计入开发时间；一局 420 s 的对局需要数分钟真实时间，请据此安排。
- 练习使用与正式比赛相同的容器和限制，不计排名，也不消耗正式比赛次数。
- 练习中你的程序只控制 4 号，**其余四台由公开的示例策略控制**；`self` 对战时双方的 4 号都是你的代码，其余仍是示例策略。示例队友只是陪练，不代表正式比赛中队友的行为。

### 8.2 结果与回放

- `results` 返回每局的胜方、判定原因、结束时间、你所在的一方（`candidate_team`）、双方队伍数据（攻击伤害、击杀、金币等），以及你的程序出错的次数（`policy_errors`）。程序出错时，`diagnostics` 会附带错误信息和最近的日志（包括 `print` 输出）。
- `replay` 把完整回放保存到 `practice/`：包括每一步的全场状态、双方动作和事件，可以用自己写的脚本分析。420 s 对局的回放约 300 MB，请按需下载。

### 8.3 提交

- `submit` 把当前 `strategy.py` 保存为一个不可修改的版本，并返回版本号。
- 可以多次提交，**截止前最后一次成功提交即参赛版本**。之前提交的版本可以用作练习对手（`--opponent 版本号`）。
- 提交前确认：练习中没有错误或超时；没有依赖 `practice/` 里的文件；最坏情况下的耗时远低于 200 ms。
- 不要把最后一次提交拖到截止前一刻，也不要把练习过但没提交的代码当成最终版本。截止后仍可查看已有的结果和回放，但不能再练习或提交。

## 9. 起步代码与策略建议

工作目录里的 `strategy.py` 已经是完整可运行的模板，可以直接在它的基础上改进。下面的最小骨架只用来说明 2027 接口，并不是一个强策略：

```python
from sdk import (action, aim_at, aim_pitch, can_fire, nearest_enemy, navigate,
                 workbench_point, launcher_ready, drones, hostile_plates, strike_plan)

def act(obs, state):
    actions = {}
    for robot in obs["robots"]:
        slot = str(robot["slot"])
        if slot not in obs["controlled_ids"]:
            continue
        try:
            actions[slot] = decide(robot, obs)
        except Exception:
            actions[slot] = action()        # 出错时原地待命，避免整个程序被停用
    return actions, state

def decide(robot, obs):
    arena = obs["arena"]
    if robot["role"] == "aerial":
        commands = {}
        plates = hostile_plates(obs, "outpost")
        for d in drones(robot):
            if not plates or d["battery_wh"] < 0.4:
                commands[str(d["index"])] = {"dock": True}
            elif d["state"] == "docked":
                commands[str(d["index"])] = {"launch": True}
            else:
                mode, value = strike_plan(d, plates[0])
                commands[str(d["index"])] = {"goto": list(value)} if mode == "approach" else {"move": list(value)}
        return action(drones=commands)
    if not robot["alive"]:
        return action(revive=True)          # 金币不足时不会生效
    if robot["role"] == "heavy" and launcher_ready(robot):
        point = workbench_point(robot, arena)
        near = abs(robot["x"] - point[0]) + abs(robot["y"] - point[1]) < 0.3
        return action(move=(0, 0) if near else navigate(robot, point, arena), install_launcher=near)
    if obs["time"] > 1.2 and robot["ammo"] < 20 and robot["role"] != "heavy":
        return action(buy_ammo={"amount": 100, "remote": True})
    enemy = nearest_enemy(robot, obs)
    if enemy is None:
        return action(posture="move") if robot["role"] == "sentry" else action()
    return action(aim=aim_at(robot, enemy), pitch=aim_pitch(robot, enemy), fire=can_fire(robot))
```

**策略建议**

- **控制度决定到时胜负。** 尽早用步兵占住对方前哨或中央高地卡 5 s，夺取对方前哨控制点；同时守住自己的前哨控制点，才能每秒 +1。能同时控制双方基地控制点（对方堡垒）时每秒 +3。
- **先让对方失去前哨控制点，才打得动基地**：对方完全控制自己的前哨控制点时，其基地免疫一切伤害。击毁对方前哨会让控制权降级；之后再占领 5 s 就能接管并把它重建成你的前哨。
- **重型的节奏**：开局取能量单元 → 1/2/3 级装配（收入、步兵等级上限、全队防御）→ 工作台装 42mm → 兑换 42mm 打前哨与基地。落后时发射机构会按时间规则提前解锁。
- **空中机器人是消耗品**：电池不在机库充电、护罩耐撞次数有限。把撞击集中在对方前哨（随时有效）或已经失去无敌的基地上，并避开对方 42mm。
- **哨兵**：开局有弹，适合守己方前哨与中央高地；进攻时用 `attack` 姿态提高冷却，危险时切 `defense` 并在关键时刻开启强化。每分钟回补给区领取 100 发。
- 用多个种子并加上 `--swap-sides` 练习，避免策略只在某一侧有效。

## 附录：常见错误

- 用 2026 的思路：以为编号有 2 号工程、以为到时先比基地血量、以为 6 号可以 `support=True` 开火。2027 的空中机器人只能撞击。
- 重型在发射机构 `fitted` 之前，或已装好但本队尚未获得使用权时发送 `fire=True`：不会发射。装上后的第一发不造成伤害。
- 安装发射机构时只发一次 `install_launcher=True`：必须在工作台停稳并**每次动作**都发送。
- 装配时没有携带能量单元，或 4 级只带了 1 枚。
- 在对方前哨控制点仍被对方完全控制时猛攻基地——基地此时无敌。
- 空中机器人一直悬停耗电：电量耗尽会坠落，而且在机库里不充电。
- 哨兵频繁切换姿态：每次切换后 5 s 内不能再切换。
- 兑换数量不是批量的整数倍（17mm 就地 10 的倍数、远程 100 的倍数；42mm 远程 10 的倍数），请求被直接忽略。
- `act` 抛出异常或超时，导致整局被停用。请在 `act` 内捕获异常，并检查最坏情况的耗时。
- 直到截止前才第一次提交。
